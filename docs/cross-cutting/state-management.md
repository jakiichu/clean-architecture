# Управление состоянием и границы слоёв

В современных фронтенд- и мобильных приложениях состояние является одним из наиболее сложных аспектов архитектуры. Неправильное распределение состояний между слоями приводит к утечкам ответственности, рассинхронизации данных, сложному тестированию и непредсказуемому поведению интерфейса.

Чистая архитектура чётко разделяет типы состояний и фиксирует, где каждый тип должен храниться, как обновляться и какие инструменты допустимы для работы с ним. Соблюдение этих границ гарантирует, что бизнес-логика остаётся изолированной, а инфраструктурные изменения не требуют пересмотра ядра системы.

## Классификация состояний

В проекте выделяются четыре независимых типа состояний. Каждый тип имеет свою зону ответственности, жизненный цикл и допустимые инструменты управления.

| Тип состояния | Описание | Примеры из предметной области | Где хранится |
|--------------|----------|------------------------------|--------------|
| **UI State** | Визуальное отображение, взаимодействие с формами, временные флаги интерфейса | Открыта ли модалка выбора пропуска, значение поля ввода телефона, флаг загрузки спиннера, выбранная вкладка в панели СБ | `App` (локальный стейт компонентов, презентеры) |
| **Server State** | Данные, источником которых является внешний API или сервис. Требуют кэширования, синхронизации и инвалидации | Список заявок на согласование, профиль пользователя, открытый криптографический ключ, статус сессии, журнал проходов | `App` (клиенты кэширования запросов) |
| **Business State** | Инварианты, правила валидации и вычисляемые результаты предметной области. Не мутируются, а вычисляются на лету | Валиден ли QR-код (проверка timestamp), разрешён ли проход по роли, процент совпадения дублей посетителя, матрица переходов статусов | `Domain` (чистые функции, DTO, интерфейсы) |
| **Persistent / Device State** | Данные, привязанные к устройству или сохраняемые между перезапусками приложения. Требуют защищённого хранения | Токен сессии, PIN-код, флаг настройки биометрии, Device Fingerprint, закешированный открытый ключ | `Data` (адаптеры SecureStore, Keychain, MMKV, SQLite) |

## Границы ответственности по слоям

### 1. UI State (Слой App)
Управляется исключительно внутри компонентов или презентеров. Не поднимается выше уровня экрана/модуля. Не синхронизируется с сервером напрямую.
- **Инструменты:** локальные стейты компонентов, библиотеки управления формами, презентеры
- **Жизненный цикл:** привязан к жизненному циклу компонента или сессии экрана
- **Правило:** не должен содержать бизнес-логику, валидацию домена или данные, полученные от API без адаптации

### 2. Server State (Слой App → Data → Domain)
Данные, которые приходят извне, кэшируются, инвалидируются и синхронизируются. Слой App только оркеструет жизненный цикл запросов, не владея бизнес-правилами.
- **Инструменты:** клиенты управления серверным состоянием (TanStack Query, SWR, Apollo, RTK Query)
- **Жизненный цикл:** управляется библиотекой кэширования (staleTime, gcTime, refetchInterval, mutation callbacks)
- **Правило:** никогда не мутируется напрямую. Обновляется только через запросы к Domain use-case. Инвалидация происходит в `onSuccess` мутаций или по событиям WebSocket/Polling.

### 3. Business State (Слой Domain)
Чистое состояние предметной области. Не хранится в глобальных переменных, а передаётся через порты и возвращается в DTO. Domain не хранит состояние между вызовами use-case.
- **Инструменты:** TypeScript интерфейсы, DTO, чистые функции валидации, результат Use-case
- **Жизненный цикл:** stateless или ephemeral. Существует только во время выполнения сценария
- **Правило:** Domain не знает о React, о кэше, о SecureStore. Он принимает Port, применяет правила, возвращает DTO. Состояние «активной сессии» или «валидного QR» — это результат проверки, а не глобальная переменная.

### 4. Persistent / Device State (Слой Data)
Низкоуровневое хранение, привязанное к ОС или устройству. Доступ осуществляется только через контракты Domain.
- **Инструменты:** адаптеры к аппаратным хранилищам (SecureStore, Keychain, Keystore), локальные БД, зашифрованные файлы
- **Жизненный цикл:** переживает перезапуски приложения, привязан к идентификатору устройства
- **Правило:** прямой импорт нативных библиотек в `App` или `Domain` запрещён. Данные возвращаются строго в формате доменных DTO.

## Паттерны взаимодействия и поток данных

Взаимодействие строится на чётких границах. Рассмотрим типичный сценарий на основе требований ТЗ (генерация динамического QR-кода):

1. **App** запускает запрос на генерацию QR через клиент серверного состояния с интервалом обновления 30 секунд.
2. **Server State** вызывает `GenerateQRCodeUseCase.execute(port)`.
3. **Domain** формирует payload `uuid:deviceId:timestamp`, валидирует временную метку, запрашивает открытый ключ через порт `ICryptoKeyProvider`.
4. **Data** (через адаптер) возвращает ключ из защищённого хранилища ОС или запрашивает свежий с сервера.
5. **Domain** шифрует payload, возвращает `IQRCodeDto`.
6. **App** получает DTO, передаёт строку в компонент отрисовки QR. Через 30 секунд запрос повторяется, предыдущий код становится невалидным на уровне бизнес-логики.

Важно: таймер ротации, состояние загрузки и отрисовка живут в `App`. Криптографические правила, формат payload и проверка timestamp живут в `Domain`. Доступ к Keychain/SecureStore живёт в `Data`.

## Рекомендации по выбору инструментов

| Задача | Допустимый инструмент | Недопустимый инструмент | Почему |
|--------|----------------------|------------------------|--------|
| Флаг «показать ошибку валидации поля» | Локальный стейт компонента/презентера | Глобальный стор, TanStack Query, SecureStore | Чистый UI-статус, не нужен вне экрана |
| Список согласованных заявок | Клиент серверного состояния (кэш + рефетч) | Zustand/Redux без инвалидации, localStorage | Серверные данные требуют кэша, синхронизации и управления жизненным циклом |
| Статус «пользователь авторизован» | `ISessionDto` из Domain + адаптер SecureStore | Глобальная переменная `window.isUserAuth`, незашифрованный сторадж | Безопасность, персистентность, тестируемость |
| Таймер ротации QR-кода | `refetchInterval` в клиенте запросов или `setInterval` в презентере | Хранение таймера в Domain | UI/синхронизационная логика, не бизнес-правило |
| Выбор темы / языка / фича-флаги | Zustand / MMKV / Preferences API | TanStack Query, Domain DTO | Клиентская настройка, не серверное состояние |

## Антипаттерны

1. **Хранение серверных данных в глобальном UI-сторе**
   Приводит к рассинхронизации, ручному управлению инвалидацией, дублированию логики кэша. Серверные данные должны управляться специализированными клиентами запросов.

2. **Вызов API напрямую из UI-компонента**
   Нарушает Dependency Rule. Компонент начинает зависеть от HTTP-клиента, что ломает тестируемость, подмену источников данных и централизованную обработку ошибок.

3. **Мутирование DTO в UI**
   DTO — это контракт Domain. Если UI меняет поля DTO перед отправкой, бизнес-логика теряет контроль над валидацией. Используйте отдельные типы форм (`IFormValues`) и маппинг в Port перед вызовом use-case.

4. **Попытка кешировать бизнес-решения**
   Результаты use-case (например, «разрешён ли проход») не должны кешироваться на уровне App, если они зависят от времени, устройства или внешних условий. Кешируйте только сырые данные, а решение вычисляйте заново через Domain.

5. **Смешивание состояний в одном хранилище**
   Объединение UI-флагов, серверных ответов и настроек устройства в одном Redux/Zustand сторе усложняет отладку, ломает DevTools и делает архитектуру хрупкой при масштабировании.

## Чек-лист проверки размещения состояния

Перед добавлением нового стейта или изменением существующего задайте вопросы:
- [ ] Это данные с сервера, которые могут измениться externally? → Клиент серверного состояния (App)
- [ ] Это настройка устройства, токен или криптографический ключ? → Адаптер SecureStore/MMKV (Data)
- [ ] Это флаг интерфейса (модалка, таб, загрузка, фокус поля)? → Локальный стейт или UI-стор (App)
- [ ] Это бизнес-инвариант, правило валидации или статус заявки? → DTO / Use-case результат (Domain)
- [ ] Нужно ли кэшировать, рефетчить, опрашивать или инвалидировать данные? → Клиент серверного состояния
- [ ] Нужно ли сохранять данные после закрытия приложения или перезагрузки устройства? → Data Layer адаптеры
- [ ] Зависит ли состояние от времени, роли или устройства? → Не кешировать в UI, вычислять в Domain при каждом вызове

Соблюдение этих границ гарантирует предсказуемость потока данных, упрощает отладку (каждый тип состояния имеет свой инспектор/инструмент) и позволяет менять инфраструктуру (переход с REST на GraphQL, смена криптобиблиотеки, обновление UI-фреймворка) без переписывания бизнес-логики или пользовательского интерфейса.
