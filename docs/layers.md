# Слои архитектуры

Архитектура проекта построена на принципе строгого разделения ответственности. Каждый слой решает свою задачу, владеет определённым типом состояния и взаимодействует с соседями только через явные контракты. В основе лежит трёхслойная модель с инверсией зависимостей:

`App → Domain ← Data`

Ниже приведено детальное описание каждого слоя, его зон ответственности, допустимых практик и типовой структуры. Описанные паттерны являются рекомендательными и могут адаптироваться под конкретный фреймворк или платформу, при условии соблюдения главного правила: **зависимости направлены только внутрь домена**.

---

## Слой App (Презентация и оркестрация)

Слой `app` отвечает за пользовательский интерфейс, обработку событий, навигацию и координацию бизнес-сценариев. Он является «тонкой прослойкой» между пользователем и ядром системы.

### Зоны ответственности
- Отрисовка компонентов и обработка пользовательских действий
- Управление UI-состоянием (загрузка, ошибки, видимость элементов, флаги интерфейса)
- Навигация, маршрутизация и защита роутов (guards)
- Вызов use-case из `domain` и адаптация результатов для отображения
- Интеграция с библиотеками управления серверным состоянием (кэширование, рефетчи, пагинация UI)

### Что разрешено
- React/Vue/Angular компоненты и хуки
- UI-кит и переиспользуемые примитивы
- Презентеры (логика подготовки данных для компонентов)
- Локальная валидация форм (синтаксическая, без бизнес-правил)
- Управление жизненным циклом запросов (TanStack Query, SWR, Apollo)

### Что запрещено
- Бизнес-правила и доменная валидация
- Прямые HTTP-запросы или работа с хранилищами
- Импорт модулей из `data` в обход `domain`
- Хранение бизнес-состояния в глобальном сторе (только UI/сессия)

### Типовая структура
```
app/
├── common/          # Сквозная инфраструктура фронтенда
│   ├── config/      # Переменные окружения, feature-flags
│   ├── providers/   # Корневые провайдеры (стор, тема, i18n, query-client)
│   ├── store/       # UI-состояние (Zustand/Redux) и сессионные флаги
│   ├── utils/       # Утилиты форматирования, debounce, работа с датами
│   └── ui-kit/      # Базовые компоненты и дизайн-токены
├── modules/         # Функциональные модули (features)
│   └── auth/
│       ├── case/    # Отдельные сценарии (login, sms-verify, biometric)
│       │   ├── presenter/  # Агрегация данных, управление формой
│       │   ├── request/    # Интеграция с TanStack Query, вызов use-case
│       │   └── component/  # Экраны и диалоги
│       └── interface/ # Локальные типы и константы модуля
└── routes/          # Конфигурация навигации и guards
```

## Слой Domain (Ядро предметной области)

Слой `domain` — центральная часть системы. Он описывает, что делает приложение с точки зрения бизнеса, без привязки к технологиям, фреймворкам или способам доставки данных.

### Зоны ответственности
- Бизнес-правила, инварианты и политики поведения
- Атомарные бизнес-сценарии (use-case)
- Доменная валидация и преобразование данных
- Описание контрактов для внешних зависимостей (порты, репозитории, DTO)

### Ключевые свойства
- Полностью независим от UI, инфраструктуры и фреймворков
- Не выполняет I/O операции (сеть, диск, камера, биометрия, SecureStore)
- Работает только с чистыми структурами данных и интерфейсами
- Легко покрывается unit-тестами без моков браузеров или эмуляторов

### Что разрешено
- Интерфейсы (порты, репозитории, use-case контракты)
- DTO (Data Transfer Objects) для передачи данных между слоями
- Чистые функции и классы, реализующие бизнес-сценарии
- Сквозные абстракции (пагинация, сортировка, базовые сущности)

### Что запрещено
- Импорт из `app` или `data`
- Использование React hooks, HTTP-клиентов, нативных модулей
- Знание о способах хранения, кэширования или отображения данных
- Побочные эффекты (логирование, аналитика, навигация)

### Типовая структура
```
domain/
├── auth/            # Предметная область: авторизация, сессии
│   ├── interface/
│   │   ├── dto/     # Форматы данных (ISessionDto, IAuthResult)
│   │   ├── port/    # Входные параметры use-case (ILoginPort)
│   │   ├── repository/ # Контракты доступа (IAuthRepository)
│   │   └── use-case/   # Контракты сценариев (IVerifySmsCodeUseCase)
│   ├── use-case/    # Реализации бизнес-сценариев
│   └── entities/    # Доменные сущности (User, Device, Session)
├── qr/              # Предметная область: генерация, валидация
├── common/          # Сквозные доменные контракты
│   ├── pagination/  # IBasePaginationPort, IBasePaginatedDto
│   └── errors/      # DomainError, ValidationError
└── index.ts         # Публичный API модуля (re-export интерфейсов)
```

## Слой Data (Инфраструктура и адаптеры)

Слой `data` реализует технические детали взаимодействия с внешним миром. Он переводит абстрактные контракты `domain` в конкретные вызовы API, работу с хранилищами или нативными модулями.

### Зоны ответственности
- Реализация репозиториев и портов из `domain`
- Выполнение сетевых запросов, работа с локальными хранилищами
- Маппинг внешних моделей (API/DB) в доменные DTO
- Обработка инфраструктурных ошибок, ретраи, трансформация статусов HTTP
- Интеграция с нативными модулями (SecureStore, LocalAuthentication, камера)

### Ограничения
- Не содержит бизнес-логики и правил принятия решений
- Не зависит от `app`
- Использует только контракты из `domain/interface`
- Возвращает данные строго в формате, ожидаемом доменом

### Что разрешено
- HTTP-клиенты (axios, fetch), интерцепторы, retry-логика
- Адаптеры к OS-level хранилищам (Keychain, Keystore, AsyncStorage)
- Мапперы (transform API response → Domain DTO)
- Singleton-инстансы репозиториев и сервисов
- Конфигурация базовых URL, таймаутов, сертификатов

### Что запрещено
- Бизнес-валидация или принятие решений на основе данных
- Знание о UI-компонентах, навигации или состояниях загрузки
- Прямой вызов use-case или обращение к презентерам
- Хранение бизнес-состояния (только кэш и персистентные данные)

### Типовая структура
```
data/
├── api/             # Сетевой слой
│   ├── client.ts    # Настроенный экземпляр axios/fetch
│   ├── interceptors/ # Auth, logging, error handling
│   └── endpoints/   # Типизированные маршруты
├── repositories/    # Реализация портов из domain
│   ├── auth/        # AuthRepository implements IAuthRepository
│   └── qr/          # QRRepository implements IQRRepository
├── storage/         # Адаптеры хранилищ
│   ├── SecureSessionStorage.ts
│   └── PinSecureStorageAdapter.ts
├── native/          # Адаптеры к нативным модулям
│   ├── BiometricAdapter.ts
│   └── DeviceInfoAdapter.ts
├── mappers/         # Преобразование внешних моделей в DTO
└── config.ts        # Базовые URL, таймауты, feature-flags инфраструктуры
```

## Правила взаимодействия между слоями

Взаимодействие строится на контрактах, а не на прямых вызовах. Это гарантирует изоляцию и заменяемость компонентов.

1. **App → Domain**: Вызывает `useCase.execute(port)`. Не знает, как реализован сценарий внутри.
2. **Domain → Data**: Обращается к репозиторию через интерфейс `IRepository`. Не знает, используется ли REST, GraphQL или локальная БД.
3. **Data → Domain**: Реализует интерфейсы, объявленные в `domain`. Возвращает строго типизированные DTO.
4. **Передача данных**: Все данные между слоями передаются через DTO. Внутренние реализации хранилищ или ответов API не просачиваются наружу.
5. **Обработка ошибок**: Инфраструктурные ошибки (сеть, таймаут, отсутствие прав) перехватываются в `data` или `app` и трансформируются в пользовательские сообщения. Доменные ошибки (невалидный payload, нарушение инвариантов) выбрасываются из `domain` и обрабатываются на уровне презентера.

## Рекомендации по организации кода

| Ситуация | Правильное размещение | Почему |
|----------|----------------------|--------|
| Валидация формата email в форме | `app/modules/.../presenter` или UI-библиотека | Синтаксическая проверка, не бизнес-правило |
| Проверка, что пользователь может генерировать QR | `domain/qr/use-cases/CanGenerateQRUseCase` | Бизнес-инвариант, зависит от статуса сессии и прав |
| Сохранение токена после входа | `data/storage/SecureSessionStorage.ts` | Инфраструктурная операция, привязана к OS |
| Отображение спиннера при загрузке | `app/common/ui/FullScreenLoader.tsx` | UI-состояние, не влияет на логику |
| Ротация криптографических ключей | `domain/crypto/use-cases/RotateKeysUseCase` | Бизнес-процесс с чёткими правилами и сроками |
| Маппинг ответа API в DTO | `data/mappers/sessionMapper.ts` | Инфраструктурная адаптация, скрывает формат бэкенда |

## Чек-лист проверки принадлежности кода к слою

Перед коммитом задайте себе вопросы:
- [ ] Содержит ли файл бизнес-правила? → Должен быть в `domain`
- [ ] Вызывает ли код сеть, хранилище или нативный модуль? → Должен быть в `data`
- [ ] Отвечает ли код за отрисовку, навигацию или UI-состояние? → Должен быть в `app`
- [ ] Импортирует ли `domain` что-то из `app` или `data`? → Нарушение Dependency Rule
- [ ] Передаются ли данные между слоями через DTO? → Да/Нет
- [ ] Можно ли заменить фреймворк или источник данных без изменения этого файла? → Да/Нет

Соблюдение этих границ обеспечивает предсказуемость рефакторинга, упрощает код-ревью и позволяет команде параллельно развивать разные части системы без конфликтов и скрытых зависимостей.
