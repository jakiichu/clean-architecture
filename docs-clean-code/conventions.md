# Проектные соглашения

До активной разработки команда выбирает не только архитектуру, но и единый способ записи кода. `function declaration` и стрелочная функция сами по себе не делают код чище или хуже. Проблема начинается, когда одинаковые задачи оформлены случайным образом и разработчик каждый раз заново угадывает стиль.

Решения фиксируются в `README`, `CONTRIBUTING.md` или локальном руководстве проекта. Форматируемые правила передаются Prettier и ESLint, а не поддерживаются вручную на ревью.

## Стиль функций

В этой документации основной стиль TypeScript-кода — **стрелочные функции**:

```ts
const calculateOrderTotal = (items: readonly IOrderItem[]): number =>
  items.reduce((total, item) => total + item.price * item.quantity, 0);

const loadOrder = async (orderId: TOrderId): Promise<IOrder> => {
  return orderRepository.getById(orderId);
};
```

Стрелочные функции используются по умолчанию для:

- use case и фабрик;
- React-компонентов и хуков;
- обработчиков и callback;
- чистых утилит;
- функций, передаваемых как значение.

Обычная декларация `function` остаётся допустимой, когда требуется её конкретное свойство:

- hoisting действительно упрощает чтение файла;
- используются overload signatures;
- нужна generator function;
- API библиотеки или существующий модуль уже последовательно использует такой стиль.

```ts
function* iteratePages(): Generator<number> {
  yield 1;
  yield 2;
}
```

Не следует механически смешивать оба варианта внутри одного модуля. Исключение должно объясняться возможностью языка или локальным соглашением, а не личным предпочтением в конкретной строке.

## Типы и интерфейсы

Принятое в проекте соглашение:

- `I` — интерфейс: `IUserRepository`, `IButtonProps`;
- `T` — type alias: `TUserId`, `TRequestStatus`;
- класс и runtime-значение не получают эти префиксы: `UserRepository`, `REQUEST_STATUS`;
- `unknown` используется для непроверенных внешних данных;
- `any` допускается только в технически неизбежной интеграционной точке с явным обоснованием.

## Имена файлов и модулей

Новый файл или каталог называется в `kebab-case`:

```text
order-history/
├── get-order-history.ts
├── order-history-repository.ts
└── order-history.test.ts
```

Модуль называется по устойчивой предметной возможности — `orders`, `hotkeys`, `vehicle-models`. Названия `utils`, `helpers`, `common`, `manager` и `service` без уточнения смысла не подходят для самостоятельного модуля: они не объясняют, за какие изменения он отвечает.

Операция внутри модуля называется действием: `create-order`, `get-order-history`, `assign-hotkey`. Нельзя одновременно использовать для одного уровня разные формы вроде `order`, `orders-module`, `order-feature` и `order-service` без различия в ответственности.

## Экспорты и границы

- Именованные экспорты используются по умолчанию.
- Default export оставляется только там, где его требует фреймворк или соглашение маршрутов.
- Публичная поверхность модуля экспортируется через один boundary-файл.
- Другой модуль не импортирует внутренние файлы в обход boundary.
- Циклические зависимости считаются дефектом границы, а не нормальным способом совместного использования.

## Остальные решения начала проекта

До первой крупной фичи фиксируются:

| Область | Что выбрать |
|---|---|
| Форматирование | кавычки, точки с запятой, длина строки, trailing comma |
| Асинхронность | `async/await`, правила fire-and-forget и cancellation |
| Ошибки | исключения, `Result` или определённое сочетание на разных границах |
| Nullability | различие `null`, `undefined` и отсутствующего поля |
| Тесты | расположение файлов, naming `describe/it`, обязательные уровни |
| Импорты | aliases, порядок групп, запрет deep imports |
| Файлы | `kebab-case`, правила для компонентов и тестов |
| Git | формат веток, коммитов и обязательные CI-проверки |

## Чек-лист

- [ ] Выбран и записан основной стиль функций.
- [ ] Исключения из выбранного стиля перечислены явно.
- [ ] Зафиксированы правила `I`/`T` и runtime-имен.
- [ ] Определено именование файлов, каталогов, модулей и операций.
- [ ] Настроены Prettier, ESLint и typecheck.
- [ ] Правила экспорта защищают публичные границы модулей.
- [ ] Команда не обсуждает автоматически проверяемый стиль вручную на каждом PR.
