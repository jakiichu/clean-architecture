# Rename (Переименование)

## Суть

Самый простой и при этом самый недооценённый рефакторинг. Переименование меняет ноль строк бизнес-логики, но может радикально улучшить читаемость.

```typescript
// ДО
function calc(x: number, y: number, t: number): number {
  return x * y * (1 - t);
}

// ПОСЛЕ
function calculateNetRevenue(price: number, quantity: number, taxRate: number): number {
  return price * quantity * (1 - taxRate);
}
```

Бизнес-логика — та же. Понимание — на порядок выше.

## Что переименовывать

- Переменные с короткими/непонятными именами: `x`, `tmp`, `data`, `obj`
- Функции с глаголами-пустышками: `process`, `handle`, `doSomething`, `manage`
- Параметры, не отражающие смысла: `a`, `b`, `value`, `item`
- Классы с суффиксами `Manager`, `Helper`, `Util`, `Service` (если они ничего не уточняют)
- Файлы, имя которых не соответствует содержимому
- Поля, которые названы как тип, а не как роль

## Как найти плохие имена

### Тест «прочитать вслух»

Прочитайте код вслух (или мысленно проговорите). Если получается косноязычная фраза — имена плохие.

```typescript
// «Если активный флаг истинный и сумма больше нуля, обработать данные»
if (a && d > 0) { proc(d); }

// «Если пользователь активен и баланс положительный, начислить бонус»
if (user.isActive && balance > 0) { creditBonus(balance); }
```

### Тест «объяснить незнакомцу»

Покажите код человеку, не знакомому с проектом. Те имена, которые требуют пояснения, — кандидаты на переименование.

### Тест «найти все вхождения»

Если имя слишком общее — поиск по нему даст десятки/сотни результатов, не связанных с вашей задачей. Хорошее имя уникально в контексте.

## Принципы хорошего имени

### 1. Имя должно говорить «почему», а не «что»

```typescript
// ❌ Описывает что хранится — но почему мы это считаем?
const number = items.length;

// ✅ Описывает смысл
const itemsInCart = items.length;
```

### 2. Длина пропорциональна области видимости

- Локальная переменная в цикле — может быть короткой (`i`, `el`)
- Поле класса — должно быть описательным
- Публичная функция — длинное, чёткое имя

```typescript
// Короткое имя в узкой области — нормально
for (let i = 0; i < items.length; i++) {
  const item = items[i];
  // ...
}

// Поле в классе должно быть описательным
class OrderProcessor {
  private pendingOrders: Order[] = []; // НЕ `arr` или `list`
}
```

### 3. Никаких загадочных сокращений

```typescript
// ❌
function calcUsrPerm(u: Usr): Perm[] { /* ... */ }

// ✅
function calculateUserPermissions(user: User): Permission[] { /* ... */ }
```

Исключения для общепринятых сокращений: `id`, `url`, `http`, `db` (если в проекте они единообразны).

### 4. Избегайте «шумовых» слов

`Data`, `Info`, `Manager`, `Handler`, `Service`, `Object` — почти всегда ничего не добавляют.

```typescript
// ❌
class UserInfoData { }
class OrderManagerService { }

// ✅
class UserProfile { }
class OrderDispatcher { }
```

### 5. Соответствие предметной области

Имена должны браться из языка домена, а не «программерского сленга».

```typescript
// ❌ Программистские термины
class DataTransferObject {
  recordList: any[];
  hashMap: Map<string, any>;
}

// ✅ Предметная область — медицина
class PatientRecord {
  visits: Visit[];
  diagnoses: Map<DiagnosisCode, Diagnosis>;
}
```

### 6. Парные имена для парных понятий

| Хорошо | Плохо |
|--------|-------|
| `start` / `stop` | `start` / `end` |
| `open` / `close` | `open` / `dismiss` |
| `add` / `remove` | `add` / `delete` |
| `first` / `last` | `first` / `final` |
| `min` / `max` | `min` / `top` |

Последовательность важнее «правильности».

## Алгоритм переименования

### Шаг 1: Найти кандидата

Любой запах: непонятная переменная, общее имя функции, класс с `Manager`.

### Шаг 2: Сформулировать роль

Запишите одной фразой: **что эта сущность делает / представляет**.

«Сумма заказа без налога»  
«Список ожидающих обработки заявок»  
«Сервис, который рассылает уведомления о доставке»

### Шаг 3: Получить имя из роли

«Сумма заказа без налога» → `subtotal`, `preTaxTotal`  
«Список ожидающих обработки заявок» → `pendingRequests`  
«Сервис рассылки уведомлений» → `DeliveryNotifier`

### Шаг 4: Использовать инструмент IDE

«Rename Symbol» (F2 в VS Code, Shift+F6 в JetBrains) меняет все вхождения, проверяет ссылки, обновляет импорты. **Не делайте этого find-and-replace по тексту** — пропустите случаи или сломаете комментарии.

### Шаг 5: Прогнать тесты

После каждого переименования. Особенно если переименовываются публичные функции/классы — где-то могло быть строковое обращение по имени (рефлексия, ORM, API).

### Шаг 6: Закоммитить

Отдельным коммитом: «rename X to Y». Не смешивайте с другими изменениями.

## Особые случаи

### Булевы переменные и функции

Используйте приставки `is`, `has`, `can`, `should`:

```typescript
// ❌
const active = true;
function login(user: User): boolean { /* ... */ }

// ✅
const isActive = true;
function canLogin(user: User): boolean { /* ... */ }
```

### Функции, возвращающие значение vs изменяющие состояние

| Возвращает | Меняет |
|------------|--------|
| `getX()`, `findX()`, `calculateX()` | `setX()`, `updateX()`, `applyX()` |

Не называйте функцию, которая что-то делает, как геттер:

```typescript
// ❌ getNextId — звучит как чтение, но генерирует и инкрементирует счётчик
function getNextId(): number {
  return ++this.counter;
}

// ✅ Имя говорит о действии
function generateNextId(): number {
  return ++this.counter;
}
```

### Коллекции

Имя — во множественном числе:

```typescript
// ❌
const order: Order[] = [];

// ✅
const orders: Order[] = [];
```

### Контекстные имена

В узком контексте можно сократить:

```typescript
class Order {
  // Внутри класса Order не надо называть items как orderItems —
  // контекст и так "order"
  items: Item[];
}
```

## Антипаттерны

### Венгерская нотация

```typescript
// ❌ Тип в имени переменной
const sName: string = 'John';
const iAge: number = 30;
const bActive: boolean = true;

// ✅ В современных языках с типами это не нужно
const name = 'John';
const age = 30;
const isActive = true;
```

### Префиксы по «слою»

```typescript
// ❌ Префикс не несёт смысла
class CUser { }
class IUserService { }  // I-префикс для интерфейсов
```

`I`-префикс для интерфейсов — спорная практика. Если в проекте есть и `User`, и `IUser` — это шум.

### Имена-каламбуры

Не называйте две разные вещи одним словом и не используйте одно слово для двух разных понятий.

```typescript
// ❌ "add" в одном месте — добавление в коллекцию, в другом — арифметика
class Cart {
  add(item: Item): void { /* добавляет в корзину */ }
}

class Calculator {
  add(a: number, b: number): number { /* складывает числа */ }
}
// Это нормально, потому что разные классы. Но не используйте `add`
// в одном классе сразу для двух смыслов.
```

## Чек-лист переименования

- [ ] Имя описывает роль/назначение, а не тип
- [ ] Длина пропорциональна области видимости
- [ ] Нет загадочных сокращений
- [ ] Нет шумовых слов (Data, Manager, Helper)
- [ ] Использованы термины предметной области
- [ ] Парные понятия названы парно
- [ ] Булевы — с `is`/`has`/`can`
- [ ] Сделано через IDE, не через find-replace
- [ ] Тесты зелёные
- [ ] Отдельный коммит

---

> Лучший комментарий к коду — это правильно подобранное имя.
