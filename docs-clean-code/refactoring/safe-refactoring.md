# Безопасный рефакторинг

## Что значит «безопасный»

Безопасный рефакторинг — это процесс, в котором на каждом шаге у вас есть **уверенность**, что код продолжает работать. Уверенность не от веры, а от:

1. Зелёных тестов
2. Малых шагов
3. Возможности откатить любой шаг

## Правила безопасности

### Правило 1: Никогда без тестов

Если на тестируемый код нет тестов — **сначала тесты, потом рефакторинг**. Иначе вы переписываете, а не рефакторите.

#### Как покрыть «легаси» без тестов

Когда тестов нет, а изменения нужны, используйте **характеризационные тесты** (characterization tests). Они фиксируют **текущее** поведение, даже если оно странное:

```typescript
// Шаг 1: запустить функцию с разными входами, записать выходы
const inputs = [
  { user: { age: 25, country: 'US' } },
  { user: { age: 17, country: 'US' } },
  { user: { age: 25, country: 'RU' } },
  { user: null },
];

inputs.forEach(input => {
  console.log(input, '→', legacyFunction(input));
});

// Шаг 2: записать эти результаты как тесты
it('returns X for adult US user', () => {
  expect(legacyFunction({ user: { age: 25, country: 'US' } })).toEqual(/* записанный результат */);
});
// ... и т.д.

// Шаг 3: теперь можно рефакторить
```

Цель — не «правильно», а «как сейчас». Если поведение странное — это будет видно по тестам, и можно будет осознанно его поменять.

### Правило 2: Один шаг — один смысл

Каждый коммит должен описываться **одним предложением без союза «и»**:

✅ «Переименовать `proc` в `processOrder`»  
✅ «Выделить функцию `validateEmail`»  
✅ «Удалить неиспользуемый параметр `verbose`»  
❌ «Переименовать переменные **и** выделить функции **и** обновить тесты»

Если в описании появилось «и» — разделите коммит.

### Правило 3: Тесты — после каждого шага

Не «когда закончу серию». Не «через пять минут». **После каждого** изменения.

```
Маленький шаг → тесты зелёные → коммит
Маленький шаг → тесты КРАСНЫЕ → откат, разбор
```

Если тесты долго гоняются — запускайте только релевантные:

```bash
# Vitest / Jest: запустить конкретный файл
npx vitest run src/order/order-service.test.ts

# Только тесты, помеченные `.only`
it.only('does the thing', () => { /* ... */ });
```

### Правило 4: Используйте IDE для механических операций

Любая операция, которую IDE умеет делать сама, должна делаться **через IDE**:

| Операция | Горячая клавиша VS Code | JetBrains |
|----------|-------------------------|-----------|
| Rename | F2 | Shift+F6 |
| Extract Function | Ctrl+Shift+R → Extract | Ctrl+Alt+M |
| Extract Variable | Ctrl+Shift+R → Extract | Ctrl+Alt+V |
| Move to file | Ctrl+. → Move | F6 |
| Change signature | — | Ctrl+F6 |

IDE-рефакторинги:
- Меняют все вхождения
- Не путают разные сущности с одинаковыми именами
- Обновляют импорты
- Не лезут в строки и комментарии (если не попросите)

### Правило 5: Версионный контроль — ваш страховой полис

#### Часто коммитьте

Каждый удачный шаг — коммит. Не накапливайте «один большой».

```
chore: rename `data` to `userPayload`
chore: extract `validatePayload` from `createUser`
chore: move `validatePayload` to `validation.ts`
chore: simplify `validatePayload` with guard clauses
```

#### Используйте ветки

Большой рефакторинг — отдельная ветка. Не блокирует основную работу, можно откатить целиком.

#### `git bisect` для поиска регрессий

Если после серии коммитов появилась проблема, а в каком — неясно:

```bash
git bisect start
git bisect bad HEAD            # сейчас сломано
git bisect good <hash 50 коммитов назад>  # тогда работало
# git помогает за log2(N) шагов найти точку поломки
```

### Правило 6: Не смешивать рефакторинг с новой функцией

Если в процессе рефакторинга появилась идея «а заодно добавлю фичу X» — **запишите в TODO и продолжайте рефакторить**.

Когда рефакторинг закончен → отдельный коммит с новой фичей.

Почему это важно:
- Ревьюер не может отличить «изменение структуры» от «изменения поведения»
- Если фича сломается — нельзя откатить только её
- Если рефакторинг ввёл регрессию — её сложно найти среди новой логики

### Правило 7: Не рефакторить «на ходу» в hotfix

Когда что-то горит в продакшене — задача одна: **починить**. Минимальный возможный фикс. Рефакторинг — потом, отдельной задачей.

## Опасные ситуации

### Изменение публичного API

Если вы переименовываете публичную функцию/класс/поле — у вас могут быть пользователи (внешние или внутренние).

**Стратегия:**
1. Добавить новую функцию/имя
2. Старое — пометить `@deprecated`, перенаправить на новое
3. Подождать, пока пользователи мигрируют
4. Удалить старое

```typescript
/**
 * @deprecated Use `calculateOrderTotal` instead. This will be removed in v2.0.
 */
export function calcTotal(order: Order): number {
  return calculateOrderTotal(order);
}

export function calculateOrderTotal(order: Order): number {
  return order.items.reduce((sum, i) => sum + i.price * i.quantity, 0);
}
```

### Рефакторинг с миграцией данных

Когда переименование/перенос поля затрагивает базу данных — это уже не «безопасный рефакторинг», это **миграция**. Требует:

- Бэкап
- Скрипт миграции с откатом
- Поэтапное развёртывание (старое поле + новое поле некоторое время существуют параллельно)

### Рефакторинг с многими потребителями

Если ваш код используют 50 других проектов (внутренний пакет, библиотека) — даже «маленькое» переименование может означать 50 PR.

В таких случаях лучше:
- Объявлять изменения заранее
- Поддерживать обе версии переходный период
- Менять мажорную версию (semver)

## Контрольные вопросы перед коммитом рефакторинга

- [ ] Поведение **не** изменилось?
- [ ] Все тесты зелёные?
- [ ] Покрытие тестами не уменьшилось?
- [ ] В коммите только структурные изменения, без новой логики?
- [ ] Описание коммита — без союза «и»?
- [ ] Публичный API не сломан?
- [ ] Если API меняется — есть `deprecated`-обёртка?
- [ ] Можно ли коммит откатить одним движением?

## Антипаттерны

### «Большой взрыв»

Месяц никаких релизов, всё переписываем. Результат: 5000 строк изменений, никто не может ревьюить, регрессии копятся, проект блокирован.

Лечение: разбейте на десятки маленьких PR, мержите по одному.

### «Эпоха очистки»

«Сейчас всё доделаю, потом неделю порефакторю». Эта неделя никогда не наступает.

Лечение: правило бойскаута — улучшайте по чуть-чуть, каждый раз когда касаетесь кода.

### «Параллельные миры»

«Сейчас перепишу с нуля, старое потом удалим». Два варианта живут параллельно, бизнес-логика расходится, в итоге — ни один не работает.

Лечение: рефакторинг **поэтапный**, в **одной** кодовой базе.

### «Тесты тоже надо переделать»

Меняем код **и** тесты одновременно. Откуда уверенность, что код по-прежнему работает? Тесты — единственный источник правды о поведении.

Лечение: код и тесты — в **разных** коммитах. Если тест устарел — сначала обновите тест с пометкой «adjust expectation to match current behavior» (если поведение меняется намеренно), потом меняйте код.

## Сводный чек-лист безопасного рефакторинга

- [ ] Перед началом — зелёные тесты
- [ ] Покрытие достаточное (характеризационные тесты, если не было)
- [ ] Маленькие шаги
- [ ] Один шаг — один смысл
- [ ] Тесты после каждого шага
- [ ] Коммит после каждого шага
- [ ] IDE-инструменты для механических операций
- [ ] Никакого смешивания с новой логикой
- [ ] Публичный API меняется через deprecation, а не разрывом
- [ ] Возможность откатить любой шаг

---

> Рефакторинг безопасен ровно в той мере, в которой вы готовы доверять своим тестам. Если не доверяете — пишите больше тестов.
