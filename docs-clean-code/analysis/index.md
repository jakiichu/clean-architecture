# Анализ кода

## Зачем анализировать код

Анализ — это умение **читать** код глазами критика. До того как что-то менять, нужно увидеть, **что именно** в нём не так. Без диагноза любое лечение — это лотерея: может, попадёшь, а может, сделаешь хуже.

Цели анализа:

- Найти места, где код плохо читается
- Заметить дублирование и связности
- Понять, где скрыты неявные предположения
- Определить, что менять в первую очередь

## Два уровня анализа

### Локальный анализ

Смотрим **на одну функцию** или **один класс**:

- Понятно ли имя?
- Помещается ли тело на экран?
- Есть ли смешение уровней абстракции?
- Сколько у функции причин для изменения?

### Системный анализ

Смотрим **на связи между модулями**:

- Какие модули знают друг о друге?
- Где есть циклические зависимости?
- Где сосредоточена «гравитация» (все знают всех)?
- Какие изменения распространяются через половину проекта?

## Симптомы плохого кода — «запахи»

Запах кода (code smell) — это **признак**, что с кодом что-то не так. Это не диагноз — это повод присмотреться внимательнее. Один запах сам по себе не приговор; но три-четыре запаха в одном месте — почти гарантия проблемы.

Подробно про запахи — в [отдельной главе](./code-smells).

## Метрики, на которые стоит смотреть

### Цикломатическая сложность
Количество независимых путей через функцию. Грубое правило:
- 1–4 — простая функция
- 5–7 — допустимо
- 8–10 — пора задуматься
- 11+ — почти наверняка нужно разбить

### Длина функции и класса
- Функция: 5–15 строк — норма, 30+ — повод присмотреться
- Класс: 100–200 строк — норма, 500+ — почти точно делает слишком много

### Глубина вложенности
Если в функции 4+ уровней вложенности (if внутри for внутри try внутри if) — почти всегда можно упростить через **ранние возвраты** или выделение функции.

```typescript
// ❌ Глубокая вложенность
function process(user: User): string | null {
  if (user) {
    if (user.isActive) {
      if (user.subscription) {
        if (user.subscription.isPaid) {
          return user.email;
        }
      }
    }
  }
  return null;
}

// ✅ Плоский код через ранние возвраты
function process(user: User): string | null {
  if (!user) return null;
  if (!user.isActive) return null;
  if (!user.subscription) return null;
  if (!user.subscription.isPaid) return null;
  return user.email;
}
```

### Количество аргументов
Если у функции 5+ аргументов — почти всегда стоит ввести параметр-объект.

### Связанность (coupling)
Сколько других модулей зависят от данного и от скольки зависит он сам. Высокая связанность — главный враг изменений.

## Процесс анализа

1. **Прочтите код вслух**. Если предложение не получается — код запутан.
2. **Объясните функцию другому человеку** (или себе вслух). Места, где «ну тут такое...», — горячие точки.
3. **Попробуйте написать тест**. Если тест требует моков на полстраницы — связность плохая.
4. **Попробуйте переименовать**. Если найти хорошее имя сложно — функция делает несколько вещей.
5. **Найдите дубликаты**. Поиск по необычным фрагментам кода часто находит копии.
