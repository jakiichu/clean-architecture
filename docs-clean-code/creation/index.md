# Создание чистого кода

## Введение

Раздел **Создание** посвящён тому, как с самого начала писать код, который будет легко читать, поддерживать и развивать. Чистый код не появляется в результате рефакторинга — он рождается в момент написания. Любая попытка «потом всё переделать» оборачивается долгом, который растёт быстрее, чем мы успеваем его выплачивать.

Перед началом работы команда фиксирует [проектные соглашения](../conventions.md). В этой документации основной стиль — стрелочные функции, интерфейсы получают префикс `I`, type alias — `T`, а новые файлы и модули называются в `kebab-case`.

## Главная идея: код пишется один раз, читается сотни раз

По разным оценкам, соотношение между чтением и написанием кода составляет **10:1**. Каждая строка, которую вы пишете, будет прочитана десятки раз — вами, вашими коллегами, тем человеком, который придёт через два года и спросит: «Что здесь происходит?».

Вывод: оптимизировать нужно **читаемость**, а не скорость написания.

```typescript
// ❌ Быстро написать, мучительно читать
const u = await db.q(`SELECT * FROM u WHERE st='a' AND ct>${t}`);

// ✅ На 10 секунд дольше, но понятно с первого взгляда
const activeUsersCreatedAfter = await userRepository.findActive({
  createdAfter: timestamp,
});
```

## Три уровня осознанности при создании кода

### Уровень 1: «Это работает»
Код запускается, тесты проходят. Программист доволен — задача выполнена.

### Уровень 2: «Это работает и не сломается завтра»
Код покрыт тестами, обработаны крайние случаи, есть валидация входных данных.

### Уровень 3: «Это работает, не сломается завтра и будет понятно через год»
Имена раскрывают намерения, функции делают одно, абстракции согласованы, нет дублирования.

Чистый код — это код **третьего уровня**.

## Принципы создания, которые мы рассмотрим в этом разделе

1. **Начало с тестов** — TDD как способ проектирования
2. **Постепенное усложнение** — от простого решения к выразительному
3. **Проектирование от использования** — сначала придумайте, как код будет вызываться
4. **Дисциплина имён** — каждое имя на счету
5. **Малые шаги** — пишите код мелкими порциями, проверяя каждую

## Парадокс новизны

Когда вы создаёте новый код, велик соблазн «сразу сделать правильно» — продумать архитектуру, выделить интерфейсы, расставить абстракции. Это часто ловушка: преждевременная абстракция вреднее дублирования.

**Правило трёх**: дублирование становится проблемой только после третьего повторения. До этого момента не пытайтесь обобщать.

```typescript
// Первая реализация - конкретно и просто
function calculateUserDiscount(user: User): number {
  if (user.subscriptionLevel === 'gold') return 0.15;
  if (user.subscriptionLevel === 'silver') return 0.10;
  return 0;
}

// Когда появилась похожая функция для продуктов - НЕ обобщайте
function calculateProductDiscount(product: Product): number {
  if (product.category === 'electronics') return 0.05;
  return 0;
}

// Только когда появилась ТРЕТЬЯ похожая функция - можно подумать об абстракции
function calculateOrderDiscount(order: Order): number {
  // ...
}

// Теперь возникает реальная необходимость в общем интерфейсе:
interface DiscountStrategy<T> {
  calculate(item: T): number;
}
```
