# Старт с нуля

## С чего начинается чистый проект

Чистый код начинается не с первой строки реализации, а с **первого решения о структуре**. То, как вы организуете файлы, директории и модули, определяет, насколько легко будет жить с этим кодом через год.

## Шаг 1: Опишите домен в одном предложении

Прежде чем создавать первый файл, ответьте на вопрос: **что делает эта система?** Одно предложение, без технических терминов.

```
✅ «Сервис принимает заказы от пользователей и доставляет их курьерам».
✅ «Приложение помогает пользователям отслеживать прочитанные книги».
❌ «Микросервис с REST API на TypeScript с PostgreSQL и Redis».
```

Второй пример — это не описание, это набор технологий. Технологии меняются, домен — нет.

## Шаг 2: Выделите главные сущности

Из описания домена выделите 3–7 ключевых понятий. Это будут ваши главные классы или модули.

Пример: «Сервис принимает заказы от пользователей и доставляет их курьерам».

Главные сущности:
- `Order` (заказ)
- `User` (пользователь, который заказывает)
- `Courier` (курьер)
- `Delivery` (процесс доставки)

Этого достаточно. Не пытайтесь сразу выделить `OrderItemPriceCalculator` или `DeliveryRouteOptimizer` — они появятся естественным образом, когда возникнет потребность.

## Шаг 3: Заложите структуру директорий по доменам, а не по типам

Худшая ошибка в начале проекта — раскладывать файлы по их **техническому типу**:

```
❌ src/
   ├── controllers/
   │   ├── OrderController.ts
   │   ├── UserController.ts
   │   └── CourierController.ts
   ├── services/
   │   ├── OrderService.ts
   │   ├── UserService.ts
   │   └── CourierService.ts
   ├── repositories/
   │   ├── OrderRepository.ts
   │   ├── UserRepository.ts
   │   └── CourierRepository.ts
   └── models/
       ├── Order.ts
       ├── User.ts
       └── Courier.ts
```

Чтобы понять, как работает заказ, нужно прыгать между четырьмя директориями.

**Лучше** — раскладывать по доменам:

```
✅ src/
   ├── order/
   │   ├── Order.ts
   │   ├── OrderRepository.ts
   │   ├── OrderService.ts
   │   └── OrderController.ts
   ├── user/
   │   ├── User.ts
   │   ├── UserRepository.ts
   │   └── ...
   ├── courier/
   │   └── ...
   └── delivery/
       └── ...
```

Всё, что относится к заказу, лежит рядом. Когда домен растёт, его можно вынести в отдельный модуль или пакет без перетасовки половины проекта.

## Шаг 4: Начните с самой простой возможной реализации

В первой версии нет места:
- кэшированию
- retry-логике
- абстрактным фабрикам
- системам плагинов
- конфигурируемым стратегиям

Всё это — ответы на проблемы, которых у вас ещё нет.

```typescript
// ✅ Первая версия - максимально просто
export class OrderService {
  constructor(private readonly db: Database) {}

  async createOrder(userId: number, items: OrderItem[]): Promise<Order> {
    const order = {
      id: generateId(),
      userId,
      items,
      status: 'pending' as const,
      createdAt: new Date(),
    };
    await this.db.insert('orders', order);
    return order;
  }
}
```

Никаких событий, очередей, кеша. Просто создание записи. Если завтра потребуется отправлять уведомление — добавите. Сегодня — не нужно.

## Шаг 5: Напишите первый тест ДО кода

Тест — это первое использование вашего кода. Если код тяжело тестировать, значит, он тяжёл в использовании.

```typescript
// 1. Сначала - тест
describe('OrderService', () => {
  it('creates an order with pending status', async () => {
    const db = createInMemoryDatabase();
    const service = new OrderService(db);

    const order = await service.createOrder(42, [
      { productId: 1, quantity: 2 },
    ]);

    expect(order.userId).toBe(42);
    expect(order.status).toBe('pending');
    expect(order.items).toHaveLength(1);
  });
});

// 2. Потом - минимальный код, чтобы тест прошёл
// 3. Потом - рефакторинг, если нужно
```

Это **TDD**: Red → Green → Refactor.

## Шаг 6: Зафиксируйте проектные соглашения

Чистые проекты живут по правилам, и правила должны быть **записаны**. Иначе через месяц вы сами их забудете, а новый разработчик не узнает никогда.

Минимум, который должен быть в README:

```markdown
## Структура проекта
- Группировка файлов по доменам (order/, user/, ...)
- Каждый домен содержит модель, репозиторий, сервис, контроллер

## Соглашения именования
- Файлы: kebab-case (order-service.ts)
- Классы: PascalCase (OrderService)
- Функции/переменные: camelCase
- Константы: UPPER_SNAKE_CASE

## Стиль функций
- Основной стиль: стрелочные функции
- `function` используется только для overload, generator или обоснованного hoisting
- В одном модуле стиль не смешивается случайным образом

## Типы
- Интерфейсы: префикс I
- Type alias: префикс T

## Тесты
- Каждый сервис покрыт unit-тестами
- Покрытие минимум 80%
- Тесты лежат рядом с кодом (order-service.test.ts)

## Команды
- npm run dev   — запуск в режиме разработки
- npm test      — тесты
- npm run lint  — проверка стиля
```

## Шаг 7: Настройте инструменты с первого дня

Линтер, форматтер и pre-commit хуки нужно настроить **до** того, как вы напишете 1000 строк кода. Потом исправлять стиль во всём проекте будет мучительно.

```json
// package.json
{
  "scripts": {
    "lint": "eslint . --ext .ts",
    "format": "prettier --write .",
    "test": "vitest",
    "typecheck": "tsc --noEmit"
  },
  "husky": {
    "hooks": {
      "pre-commit": "npm run lint && npm run typecheck"
    }
  }
}
```

## Чек-лист старта нового модуля

- [ ] Описание домена в одном предложении
- [ ] Выделены 3–7 главных сущностей
- [ ] Структура директорий по доменам
- [ ] Первый тест написан до кода
- [ ] README с правилами проекта
- [ ] Настроены линтер, форматтер, тесты
- [ ] Pre-commit хуки запускают проверки
- [ ] Самая простая реализация без оптимизаций

## Главный принцип старта

**Не решайте проблем, которых у вас нет**. Не вводите абстракции «на будущее», не пишите конфигурируемых стратегий «вдруг понадобится», не оборачивайте всё в интерфейсы «для тестов».

Чистый старт — это **минимально достаточная** структура, в которой легко добавить сложность тогда, когда она станет реально нужна.
