# Обзор архитектуры

Проект использует три основных слоя: `App`, `Domain` и `Data`. Разделение строится не вокруг технических папок, а вокруг разных причин для изменения:

| Причина изменения | Слой |
|---|---|
| Изменилось отображение, взаимодействие или навигация | `App` |
| Изменилось бизнес-правило или сценарий | `Domain` |
| Изменился API, формат данных, хранилище или способ синхронизации | `Data` |

Цель такого разделения — не запретить слоям взаимодействовать, а сделать это взаимодействие явным и не позволить заменяемым деталям управлять ядром системы.

## Два направления, которые нельзя путать

В архитектуре одновременно существуют **направление выполнения** и **направление зависимости исходного кода**.

### Направление выполнения

Во время пользовательского сценария вызовы могут проходить через все слои:

```text
App → Domain → Repository implementation → Data Source
```

Например, ViewModel запускает use case, use case вызывает `TripRepository`, реализация репозитория обращается к IndexedDB или API.

### Направление зависимости

На уровне импортов картина другая:

```text
App ───────→ Domain ←────── Data
                 ↑
          contracts/models
```

- `App` импортирует сценарии и типы Domain;
- `Data` импортирует контракты и модели Domain, чтобы реализовать их;
- `Domain` не импортирует ни `App`, ни `Data`.

Use case действительно вызывает метод репозитория, но зависит только от интерфейса, принадлежащего Domain. Конкретная реализация подставляется снаружи через Dependency Injection.

Это различие объясняет, почему фраза «Domain обращается к Data» допустима при описании выполнения, но неверна при описании импортов.

## Правило зависимостей

Главное правило проекта:

> Код, описывающий бизнес-смысл, не должен зависеть от кода, описывающего способ доставки, хранения или отображения данных.

### Разрешено

- `App` вызывает use case из `Domain`;
- `App` преобразует результат сценария в UI Model;
- `Data` реализует интерфейсы, объявленные в `Domain`;
- `Data` преобразует внешние DTO и модели хранения в доменные модели;
- Composition Root знает о конкретных реализациях обоих внешних слоёв и связывает их;
- чистые общие типы импортируются через явно определённый публичный API.

### Запрещено

- `Domain` импортирует React, роутер, HTTP-клиент или библиотеку хранения;
- `Domain` импортирует модули из `App` или `Data`;
- `Data` импортирует компоненты, ViewModel или UI State;
- UI напрямую вызывает API или локальную базу в обход сценария и архитектурного контракта;
- DTO конкретного сервиса или структура таблицы базы просачивается в Domain и App;
- use case создаёт конкретный репозиторий внутри себя.

## Слой App

`App` адаптирует приложение к пользователю и среде отображения.

### Отвечает за

- React-компоненты и экраны;
- ViewModel и обработку пользовательских действий;
- UI State: загрузку, успех, пустое состояние и ошибку;
- UI Effects: навигацию, toast, фокус и системные диалоги;
- UI-модели, локализацию и форматирование;
- маршрутизацию и presentation-проверки доступа;
- интеграцию сценариев с жизненным циклом React.

### Не отвечает за

- бизнес-инварианты;
- выбор между удалённым и локальным источником;
- структуру HTTP-запросов и ответов;
- сериализацию и миграции хранилища;
- технические retry- и cache-policy репозитория.

ViewModel может быть кастомным React-хуком. Это форма реализации, а не повод переносить в хук обязанности Domain или Data.

## Слой Domain

`Domain` описывает систему на языке предметной области и не знает, в каком интерфейсе или на какой платформе она запущена.

### Отвечает за

- сущности, объекты-значения и агрегаты;
- инварианты и бизнес-политики;
- законченные пользовательские и системные use case;
- domain-сервисы для чистых алгоритмов;
- команды и результаты сценариев;
- контракты репозиториев и внешних провайдеров;
- стабильные доменные ошибки.

### Не отвечает за

- сетевые запросы, базу, файлы и браузерные API;
- UI State, тексты ошибок и навигацию;
- кэш React-библиотеки;
- DTO конкретного API и модели таблиц;
- создание конкретных инфраструктурных зависимостей.

Domain не обязательно состоит только из классов. Его можно реализовывать функциями, типами и объектами. Важно отсутствие инфраструктурных зависимостей и наличие выраженной бизнес-семантики.

## Слой Data

`Data` адаптирует внешние системы к ожиданиям Domain.

### Отвечает за

- реализации репозиториев и других выходных портов;
- Remote, Local и System Data Source;
- HTTP-клиенты, базы, файловую систему и SDK;
- внешние DTO и persistence-модели;
- мапперы, сериализаторы и парсеры;
- техническое кэширование и выбор источника;
- offline-first и синхронизацию;
- преобразование низкоуровневых ошибок в стабильные ошибки приложения.

### Не отвечает за

- пользовательские бизнес-сценарии;
- правила допустимости действий;
- состояние компонентов и навигацию;
- подготовку локализованного текста;
- принятие решений, смысл которых относится к предметной области.

Реализация репозитория может содержать техническую координацию: прочитать локальную запись, проверить срок актуальности, запросить сеть, сохранить результат и вернуть fallback. Это Data-логика. Решение «разрешено ли пользователю выполнить действие» является бизнес-логикой и остаётся в Domain.

## Модели данных и их владельцы

Выражение «DTO между слоями» слишком расплывчато и скрывает важные различия. В проекте используются отдельные модели для разных границ:

| Модель | Владелец | Назначение |
|---|---|---|
| `WeatherResponseDto` | `Data` | Отражает контракт внешнего API |
| `CachedWeatherEntity` | `Data` | Отражает формат локального хранения |
| `WeatherForecast` | `Domain` | Выражает бизнес-смысл прогноза |
| `GetTripOverviewResult` | `Domain` | Результат законченного сценария |
| `TripOverviewUiModel` | `App` | Данные в форме, удобной для View |

Типичный путь преобразований:

```text
API DTO ──mapper──→ Domain Model ──UI mapper──→ UI Model
   Data                 Domain                     App
```

При сохранении направление может быть обратным:

```text
Domain Model ──mapper──→ Persistence Model
```

Маппинг выполняется на той стороне границы, которая знает внешний формат. Поэтому API DTO и persistence-модели остаются в Data, а UI Model — в App.

## Полный поток сценария

Рассмотрим загрузку обзора поездки:

1. View сообщает ViewModel, что экрану нужны данные.
2. ViewModel вызывает `GetTripOverview` с доменным идентификатором.
3. Use case запрашивает поездку через `TripRepository`.
4. Use case запрашивает погоду и места через соответствующие контракты.
5. Реализации репозиториев выбирают подходящие Data Source и политики обновления.
6. Data Source получают внешние DTO или persistence-модели.
7. Data преобразует их в модели, ожидаемые Domain.
8. Use case применяет правила и собирает `TripOverview`.
9. ViewModel преобразует результат в `TripOverviewUiModel` и обновляет UI State.
10. View только отображает полученное состояние.

```text
View
  ↓ action
ViewModel
  ↓ command
Use Case
  ↓ repository contract
Repository Implementation
  ↓
Remote / Local Data Source
  ↑ external data
Repository Implementation
  ↑ domain model
Use Case
  ↑ result
ViewModel
  ↑ UI state
View
```

## Где живут побочные эффекты

Не все побочные эффекты относятся к одному слою:

- сеть, диск, часы устройства и системные API исполняются адаптерами Data;
- навигация, toast и управление фокусом исполняются App;
- Domain только выражает необходимость внешней операции через контракт или возвращаемый результат.

Например, Domain может зависеть от интерфейса `Clock`, но не вызывает `Date.now()` напрямую. Data предоставляет системную реализацию, а тест передаёт управляемые часы.

## Серверный кэш и доменный репозиторий

TanStack Query и доменный Repository решают разные задачи:

- клиент запросов управляет состоянием асинхронной операции для UI: подписками, refetch и жизненным циклом экрана;
- Repository скрывает источники данных и выдаёт Domain согласованную модель;
- инфраструктурный кэш репозитория поддерживает offline-first и не зависит от наличия React-компонента.

Иногда приложению достаточно кэша клиента запросов, и отдельный постоянный кэш в Data не нужен. В более сложном offline-first сценарии оба механизма могут существовать одновременно, но у них должны быть явно разделены владельцы и правила актуальности.

## Composition Root

Поскольку Domain знает только интерфейсы, конкретные зависимости нужно связать на внешней границе:

```text
createTripRepository(
  remoteTripDataSource,
  localTripDataSource,
  clock,
)

createGetTripOverview({
  tripRepository,
  weatherRepository,
  placeRepository,
})
```

Composition Root может импортировать и Domain, и Data. Он создаёт граф объектов, но не содержит бизнес-правил, маппинга ответов или UI-поведения.

## Модульность

Слои отвечают на вопрос «какой это тип ответственности», а feature-модули — «к какой предметной области относится код». Эти способы организации дополняют друг друга.

Модуль должен:

- экспортировать небольшой публичный API;
- скрывать детали реализации;
- не обращаться к внутренним файлам соседнего модуля;
- владеть своими сценариями и моделями;
- переносить действительно общие понятия в `common` только после появления подтверждённого переиспользования.

`common` не должен становиться местом для кода, владельца которого пока не удалось определить.

## Архитектурные проверки

При ревью изменения полезно проверить:

- Можно ли заменить API или хранилище без изменения Domain?
- Можно ли изменить View без изменения бизнес-сценария?
- Можно ли протестировать use case без React и реального I/O?
- Не покинул ли внешний DTO слой Data?
- Не принимает ли Repository бизнес-решение?
- Не создаёт ли use case конкретную инфраструктурную зависимость?
- Определён ли владелец кэширования и состояния?
- Защищает ли новая абстракция реальную границу?

## Эволюция архитектуры

Архитектура является рабочей моделью, а не догмой. Её следует менять, когда появляются новые требования или текущие границы перестают локализовать изменения.

Значимые решения фиксируются в ADR:

1. контекст и проблема;
2. рассмотренные варианты;
3. принятое решение;
4. положительные и отрицательные последствия;
5. условия, при которых решение стоит пересмотреть.

Изменения лучше выполнять постепенно по сценариям или модулям, сохраняя работающую систему и добавляя проверки границ в линтер, тесты или анализ зависимостей.
