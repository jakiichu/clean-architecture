# Стандарты написания кода

Единый стиль кода — основа поддерживаемости проекта, скорости код-ревью и предотвращения архитектурных нарушений. Данный раздел фиксирует обязательные правила, применяемые ко всем файлам в репозитории. Отклонения от стандартов допускаются только при согласовании с тимлидом и фиксацией причины в комментарии или ADR.

## 1. Функции и синтаксис

- Всегда приходить к общему написанию стилей функций
- Анонимные функции допустимы только как inline-обработчики в JSX, если они не выносят логику за пределы рендера
- Асинхронные операции оформляются через `async/await`, промисы без `await` допускаются только в fire-and-forget сценариях с явным `.catch()`

## 2. Именование переменных и констант

- Всегда писать полные, осмысленные названия переменных. Сокращения допускаются только для общепринятых аббревиатур (`id`, `url`, `api`, `dto`, `ui`)
- Формат: `camelCase` для переменных, функций, параметров
- Формат: `PascalCase` для компонентов, классов, интерфейсов, типов
- Формат: `UPPER_SNAKE_CASE` для констант, конфигурационных объектов, enum-подобных структур
- Булевы переменные начинаются с префиксов: `is`, `has`, `should`, `can`
- Обработчики событий начинаются с `handle`: `handleSubmit`, `handlePressBack`
- Коллбэки и замыкания, возвращающие данные, начинаются с `get` или `fetch`

## 3. Типизация и интерфейсы

- Все интерфейсы пишутся с префиксом `I`: `IUserProfile`, `IAuthRepository`, `IUseCase`
- Запрещено использовать `any`. При невозможности строгой типизации использовать `unknown` с последующим type guard или приведением через `as` только после валидации
- Пропсы компонентов типизируются через интерфейсы: `IButtonProps extends TouchableOpacityProps`
- Ответы API и данные из хранилищ маппятся в DTO сразу на границе слоя `data`

## 4. Организация экспортов

- Все экспорты из файла пишутся строго в конце файла
- Использовать именованные экспорты для утилит, хуков, типов, интерфейсов
- Default-экспорт допускается только для React-компонентов экранов и корневых провайдеров
- Файлы-индексы (`index.ts`) реэкспортируют публичный API модуля, скрывая внутреннюю реализацию
- Запрещено смешивать логику и экспорты в середине файла

Пример структуры файла:
```
// imports
// interfaces/types
// constants
// component/hook/logic
// styles
// exports (в конце)
```

## 5. Маршрутизация и ключи навигации

- Конструкция `type RouteKeys = keyof typeof ROUTES;` заменяется на `ERouteKeys` для единообразия с enum-паттерном
- Объект с путями объявляется как `const ROUTER_PATH = { ... } as const`
- Все переходы выполняются через типизированный роутер: `router.replace(ROUTER_PATH.AUTH_PHONE)`
- Хардкод строк путей в компонентах запрещён

## 6. Запрещённые практики

- Использование `any` в сигнатурах функций, пропсах, стейте
- Прямые импорты из `data` в `app` в обход `domain`
- Бизнес-логика внутри UI-компонентов или хуков презентации
- Мутация пропсов или стейта напрямую (только через setState/immer)
- Глобальные переменные вне `config` или `constants`
- Игнорирование ошибок через пустой `catch {}` или `// @ts-ignore` без комментария с обоснованием
- Дублирование типов DTO между слоями без маппинга

## 7. Коммиты и Git-flow

- Формат коммита: `type(scope): description`
- Типы: `feat`, `fix`, `refactor`, `docs`, `style`, `test`, `chore`
- Описание на английском, начинается с глагола в infinitive, без точки в конце
- Ветка: `feature/short-description`, `fix/issue-123`, `refactor/auth-module`
- Перед merge обязателен проход линтера, тип-чекера и успешная сборка dev-билда
- Конфликты решаются автором фичи, rebasing предпочтительнее merge-коммитов

## 8. Автоматизация и проверка

- ESLint + Prettier настроены на pre-commit hook через husky/lint-staged
- `tsc --noEmit` запускается в CI перед сборкой
- Запрещено коммитить файлы с `console.log`, `debugger`, временными заглушками
- Конфигурации линтера и тайпскрипта находятся в корне, изменения согласуются командой

Соблюдение данных стандартов гарантирует предсказуемость кодовой базы, упрощает ревью и позволяет новым разработчикам входить в проект без изучения скрытых договорённостей. Архитектурные правила имеют приоритет над стилистическими, но оба слоя требований обязательны к исполнению.
