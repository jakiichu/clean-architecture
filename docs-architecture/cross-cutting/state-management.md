# Управление состоянием и границы слоёв

Состояние нельзя правильно разместить только по признаку «оно меняется». Сначала нужно определить:

1. что это состояние означает;
2. кто является источником истины;
3. какой у него жизненный цикл;
4. кто имеет право его изменять;
5. требуется ли восстановление после перезапуска;
6. какие правила определяют его корректность.

Одна и та же информация может одновременно иметь разные представления. Например, поездка существует как доменная модель, запись IndexedDB, значение query-кэша и UI Model экрана. Это не четыре независимых источника истины: каждое представление принадлежит своей границе и должно иметь понятный способ обновления.

## Основные категории состояния

| Категория | Пример | Владелец |
|---|---|---|
| **Ephemeral UI State** | Открыта ли панель, фокус, hover, drag-and-drop | Компонент или Compound Component в `App` |
| **Screen State** | Загрузка, ошибка, выбранный день, данные экрана | ViewModel в `App` |
| **Form State** | Введённые значения, touched, локальные ошибки | Форма или ViewModel в `App` |
| **Navigation State** | Текущий маршрут, параметры URL, история | Router в `App` |
| **Remote State** | Актуальные данные внешнего сервиса | Внешний сервис; локальные представления — `Data` и `App` |
| **Domain State** | Trip, её дни и допустимые переходы | Модель и правила `Domain` |
| **Persistent Local State** | Локальная поездка, очередь синхронизации | Хранилище через `Data` |
| **Device Preference** | Тема, язык, настройка reader | `App` определяет смысл, `Data` обеспечивает хранение |
| **Secret State** | Токен, ключ шифрования | Защищённое хранилище через `Data` |

Категории могут пересекаться по данным, но не по ответственности. Например, выбранный `tripId` может находиться в URL, ViewModel загружает по нему `Trip`, Data хранит запись, а Domain проверяет инварианты самой поездки.

## Источник истины

Источник истины — место, относительно которого разрешаются расхождения.

```text
Remote authoritative data → сервер
Offline-created trip      → локальная БД до синхронизации
Business invariant        → Domain
Selected tab              → View или URL
Access token              → защищённое хранилище
```

Нельзя объявить любой кэш «источником истины» только потому, что UI читает из него данные. Кэш является копией, если не определены правила владения изменениями и синхронизации.

Для offline-first модели источник истины может быть локальным. Тогда UI наблюдает локальную базу, изменения сначала фиксируются в ней, а синхронизация согласует их с сервером. Это архитектурное решение должно быть явным.

## Ephemeral UI State

Краткоживущее presentation-состояние хранится максимально близко к потребителю:

```tsx
function PlacePicker() {
  const [isOpen, setOpen] = useState(false);
  const [highlightedIndex, setHighlightedIndex] = useState(0);
}
```

Сюда относятся:

- открытие popover и modal;
- состояние фокуса;
- hover и pressed;
- временная анимация;
- индекс подсвеченного элемента;
- локальное состояние drag-and-drop.

Его не следует помещать в глобальный store, Domain или постоянное хранилище без отдельной причины.

## Screen State и ViewModel

ViewModel владеет состоянием законченного экрана или UI-сценария:

```ts
type TTripDetailsUiState =
  | { status: 'loading' }
  | { status: 'not-found' }
  | { status: 'error'; message: string; canRetry: boolean }
  | { status: 'success'; trip: TripDetailsUiModel };
```

Discriminated union делает невозможными противоречивые сочетания вроде:

```ts
{
  isLoading: true,
  error: 'Не удалось загрузить',
  data: { /* ... */ },
}
```

ViewModel:

- запускает use case;
- преобразует результат в UI Model;
- определяет presentation-состояние;
- предоставляет View действия;
- не становится источником бизнес-инвариантов.

Если данные нужны нескольким экранам, это не означает автоматически, что их следует перенести в глобальный UI-store. Возможно, источником уже является query-кэш, URL, локальная база или Repository.

## Состояние Compound Components

Compound Component может владеть состоянием, которое относится только к внутренней композиции View:

```tsx
<TripPlanner state={state} actions={actions}>
  <TripPlanner.Days />
  <TripPlanner.PlaceSuggestions />
</TripPlanner>
```

В Context допустимы:

- UI State;
- UI Actions;
- состояние визуального выбора;
- presentation-конфигурация;
- refs для фокуса и доступности.

Repository, Data Source и конкретные use case в такой Context не передаются. Подробнее: [Compound Components и MVVM](../compound-components.md).

## Form State

Форма владеет черновиком пользовательского ввода:

```ts
type TCreateTripFormValues = {
  destination: string;
  startDate: string;
  endDate: string;
};
```

Перед запуском сценария ViewModel преобразует его в Command:

```text
TCreateTripFormValues
        ↓ App mapper
CreateTripCommand
        ↓ Domain
CreateTrip
```

В App допустима синтаксическая валидация для быстрой обратной связи. Domain всё равно защищает бизнес-инварианты, потому что use case может быть вызван не только этой формой.

Черновик следует сохранять постоянно только при явном пользовательском требовании. В таком случае App определяет момент сохранения и восстановления, а Data предоставляет порт хранилища.

## Navigation State

Маршрут является частью состояния интерфейса. Если выбранное значение должно:

- сохраняться после перезагрузки страницы;
- участвовать в deep link;
- поддерживать Back/Forward;
- быть доступно по прямой ссылке,

то URL обычно является лучшим владельцем, чем локальный `useState`.

Route params остаются строковыми внешними данными. App валидирует и преобразует их в доменные значения до вызова use case.

## Domain State

Domain владеет смыслом и корректными переходами модели:

```ts
const updatedTrip = trip.addPlace(date, place);
```

Метод `addPlace` может:

- проверить, что дата входит в период поездки;
- запретить дубликат;
- сохранить корректность агрегата;
- вернуть новую модель или доменную ошибку.

Domain не обязан быть глобальным in-memory store. Доменная модель может жить только во время use case, сохраняться через Repository и восстанавливаться при следующем вызове. Но утверждение «Domain всегда stateless» тоже слишком сильное: Entity и Aggregate именно представляют состояние предметной области, а долгоживущие доменные процессы могут требовать явно смоделированного жизненного цикла.

Важно другое: Domain не хранит состояние в React, Zustand, browser storage или модульной глобальной переменной.

## Remote State и query-кэш

TanStack Query управляет **presentation-проекцией асинхронного результата**:

- подписками компонентов;
- статусом загрузки;
- временем устаревания;
- повторным выполнением;
- отменой и дедупликацией;
- жизненным циклом неактивной записи.

Query function вызывает use case, а не HTTP-клиент:

```ts
useQuery({
  queryKey: ['trip-overview', tripId],
  queryFn: () => getTripOverview.execute({ tripId }),
});
```

Query-кэш не заменяет Repository:

| Query-кэш | Repository/Data cache |
|---|---|
| Привязан к потребностям App | Скрыт за контрактом Domain |
| Управляет подписками UI | Управляет источниками данных |
| Хранит результат query function | Хранит внешнюю или persistence-модель |
| Часто живёт в памяти | Может переживать перезапуск |
| Знает о refetch экрана | Знает об offline-first и синхронизации |

Для простого online-приложения query-кэша может быть достаточно. Для offline-first приложения постоянный кэш и правила синхронизации принадлежат Data, даже если App дополнительно использует TanStack Query.

### Инвалидация после команды

После успешного изменения ViewModel или request-adapter может инвалидировать presentation-запрос:

```ts
await addPlaceToTripDay.execute(command);

await queryClient.invalidateQueries({
  queryKey: ['trip-overview', command.tripId],
});
```

Это не бизнес-правило, а способ обновить отображение. Сам use case уже должен сохранить корректное доменное изменение через Repository.

## Persistent Local State

Постоянное состояние хранится через Data:

```text
Domain contract
      ↑ implemented by
Repository
      ↓
Local Data Source
      ↓
IndexedDB / SQLite / File
```

Data отвечает за:

- схему и миграции;
- persistence-модели;
- сериализацию;
- транзакции;
- техническое шифрование;
- восстановление после I/O-сбоев.

Domain определяет смысл операции: сохранить поездку, получить историю, записать прогресс чтения. Он не определяет таблицу, ключ localStorage или формат JSON.

### Хранение пользовательских переопределений

Для настраиваемой функциональности полезно разделять три значения:

```text
Definition + Override → Effective Configuration
```

- `Definition` — поставляемая приложением стандартная конфигурация;
- `Override` — сохранённое решение пользователя;
- `Effective Configuration` — фактически действующее вычисленное значение.

В persistent storage обычно следует сохранять только override:

```typescript
interface IShortcutOverride {
  readonly actionId: string;
  readonly combination: ShortcutCombination;
}
```

Полный effective catalog хранить не нужно. Иначе стандартное значение незаметно превращается в пользовательское и перестаёт обновляться вместе с приложением.

Рассмотрим изменение стандартного сочетания:

```text
версия 1: global-search.open → Alt+/
версия 2: global-search.open → Primary+K
```

Если пользователь не изменял команду, после обновления он должен получить новое стандартное значение. Это происходит автоматически, когда override отсутствует:

```text
new definition + no override → new effective value
```

Если вместо override была сохранена полная effective configuration версии 1, приложение не сможет отличить старое стандартное значение от осознанного пользовательского выбора.

### Явное отключение и отсутствие настройки

Отсутствие override означает «использовать definition», а не «отключить функцию». Отключение моделируется явно:

```typescript
type TShortcutOverride =
  | {
      readonly type: 'assigned';
      readonly actionId: string;
      readonly combination: ShortcutCombination;
    }
  | {
      readonly type: 'disabled';
      readonly actionId: string;
    };
```

Тогда операции имеют однозначный смысл:

| Операция | Изменение persistent state |
|---|---|
| Назначить пользовательское значение | сохранить `assigned` override |
| Отключить | сохранить `disabled` override |
| Сбросить одно значение | удалить override |
| Сбросить всё | удалить все override |

### Где вычислять effective configuration

Если применение override содержит устойчивые правила продукта, вычисление принадлежит Domain. App может хранить загруженные override в памяти и запрашивать вычисленный результат:

```text
App State: loaded overrides
Domain: resolve(definitions, overrides)
View: effective UI model
```

Data не решает, какой override допустим и конфликтуют ли настройки. Он отвечает за сериализацию, runtime-валидацию внешних данных, миграции и восстановление после ошибок чтения.

Effective configuration является производным состоянием. Не следует независимо обновлять одновременно:

```text
overrides state
effective state
```

Иначе появляются два источника истины. Без специальной причины достаточно хранить override и пересчитывать effective result.

### Версионирование каталога и очистка устаревших override

После удаления действия в persistent storage может остаться override с неизвестным `actionId`. На Data-границе возможны две стратегии:

1. игнорировать неизвестную запись при чтении;
2. мигрировать хранилище и физически удалить её.

Первая стратегия проще и безопасна как fallback. Вторая полезна, если формат данных версионируется или старые записи способны заметно увеличивать хранилище.

Нельзя автоматически подставлять неизвестную запись в Domain через type assertion. Данные после `JSON.parse` имеют тип `unknown` и проходят runtime-валидацию.

Подробнее: [пример менеджера горячих клавиш](../examples/hotkey-manager.md).

## Offline-first состояние

Offline-first требует явной модели, а не только `networkMode: 'offlineFirst'`.

Необходимо определить:

- локальный источник истины;
- идентификаторы локально созданных объектов;
- очередь неподтверждённых изменений;
- статусы `pending`, `synced`, `failed`;
- правила повторов;
- разрешение конфликтов;
- поведение удаления;
- отображение устаревших данных;
- момент фоновой синхронизации.

Типичный поток локального изменения:

```text
Command
  ↓
Use Case изменяет Aggregate
  ↓
Repository сохраняет локально + создаёт Sync Operation
  ↓
UI наблюдает локальный результат
  ↓
Sync Worker отправляет изменение
  ↓
Repository подтверждает или фиксирует конфликт
```

UI не должен вручную склеивать удалённый ответ с локальной очередью. Data возвращает согласованное представление через Repository.

## Device Preferences и Secret State

Не все постоянные данные одинаковы.

| Данные | Подходящее хранение |
|---|---|
| Тема и плотность интерфейса | Preferences, localStorage, MMKV |
| Последняя открытая вкладка | URL или обычное локальное хранилище |
| Access token | SecureStore, Keychain, Keystore |
| Ключ шифрования | Аппаратно защищённое хранилище |
| Большой offline-каталог | IndexedDB или SQLite |

App может владеть смыслом настройки, но не импортирует конкретную библиотеку хранения. Для чувствительных данных выбор хранилища является частью модели безопасности, а не только удобства.

## Производное состояние

Производное значение лучше вычислять, чем синхронизировать вручную:

```ts
const selectedDay = state.days.find(
  (day) => day.id === state.selectedDayId,
);
```

Хранение одновременно `selectedDayId` и отдельной копии `selectedDay` создаёт риск рассинхронизации.

Однако место вычисления зависит от смысла:

- локализованная подпись — App;
- бизнес-статус поездки — Domain;
- признак свежести cache record — Data.

Не всякое вычисляемое значение является бизнес-логикой.

## События и состояние

UI Effect не следует смешивать с устойчивым UI State:

```ts
type TTripPlannerEffect =
  | { type: 'navigate'; to: string }
  | { type: 'show-toast'; message: string }
  | { type: 'focus-field'; field: 'destination' };
```

Если одноразовое событие хранить как обычный флаг, оно может повториться после повторного рендера или восстановления состояния. Механизм эффектов должен явно учитывать одноразовое потребление.

Доменное событие имеет другой смысл: оно фиксирует значимый факт предметной области, например `TripCreated`. Его нельзя автоматически превращать в toast или analytics event внутри Domain. App и внешние адаптеры решают, как на него реагировать.

## Глобальное состояние

Глобальный store оправдан, когда UI-состояние:

- используется далёкими независимыми ветками дерева;
- должно переживать смену маршрута;
- не имеет более естественного владельца в URL, query-кэше или Domain;
- требует координации между несколькими экранами.

Примеры: тема, состояние глобальной панели, пользовательские presentation-настройки.

Не следует переносить данные в Zustand или Redux только потому, что они нужны двум компонентам. Сначала проверьте локальное поднятие состояния, композицию, Context, URL и существующий query-кэш.

## Антипаттерны

### Один store для всего

UI-флаги, ответы API, токены и доменные объекты получают одинаковый жизненный цикл и неясные правила обновления.

### Дублирование серверных данных

Копирование результата TanStack Query в Zustand создаёт два кэша. Если специальная копия действительно нужна, должны быть определены её владелец, направление синхронизации и причина существования.

### Мутирование Domain Model в UI

View не должна обходить методы Aggregate или создавать невалидное состояние. Пользовательское действие передаётся ViewModel и далее в use case.

### Сохранение внешнего DTO как модели приложения

API DTO меняется вместе с сервисом и принадлежит Data. Сначала он преобразуется в persistence- или Domain Model.

### Кэширование бизнес-решения без зависимостей

Значение `canEditTrip` может зависеть от роли, времени и статуса поездки. Если его кэшировать, ключ и инвалидация должны учитывать все зависимости. Часто безопаснее пересчитать правило в Domain.

### Context как Service Locator

Context Compound Component не должен предоставлять репозитории и инфраструктурные сервисы. Это скрывает зависимости View и обходит ViewModel.

## Выбор инструмента

| Задача | Основной владелец/инструмент |
|---|---|
| Открытие modal | локальный `useState` |
| Состояние сложного экрана | ViewModel, `useReducer` или state machine |
| Поля формы | form library или локальный reducer |
| Фильтр, отражаемый в ссылке | URL/search params |
| Асинхронный результат для экрана | TanStack Query поверх use case |
| Доменное изменение | Entity/Aggregate через use case |
| Offline-каталог | Repository + Local Data Source |
| Очередь синхронизации | Data sync subsystem |
| Тема приложения | UI-store + preferences adapter |
| Access token | secure storage adapter |

Инструмент выбирается после определения владельца, а не наоборот.

## Чек-лист

- [ ] Определён источник истины.
- [ ] Понятен жизненный цикл состояния.
- [ ] Есть единственный владелец изменения.
- [ ] Производные значения не дублируются без причины.
- [ ] Для пользовательской конфигурации разделены definition, override и effective result.
- [ ] Сброс к стандартному удаляет override, а не сохраняет копию default value.
- [ ] API DTO не используется как состояние App или Domain.
- [ ] Query-кэш не подменяет offline-хранилище неявно.
- [ ] Глобальный store выбран после проверки более локальных вариантов.
- [ ] Бизнес-переход выполняется через Domain.
- [ ] UI Effect не хранится как обычный долговечный флаг.
- [ ] Секреты находятся в подходящем защищённом хранилище.
- [ ] Для offline-first определены конфликты и очередь изменений.
- [ ] Context Compound Component содержит только presentation API.
