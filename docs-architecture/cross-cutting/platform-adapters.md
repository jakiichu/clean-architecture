# Платформенные адаптеры

Браузер, операционная система и нативный SDK поставляют приложению нестабильные внешние контракты: события клавиатуры, разрешения, состояние сети, хранилище, камеру и биометрию. Платформенный адаптер переводит такой контракт в язык приложения и не позволяет деталям среды проникнуть во внутренние слои.

## Сначала определить направление взаимодействия

Место адаптера зависит не от названия API, а от роли взаимодействия.

| Взаимодействие | Контракт | Реализация | Пример |
|---|---|---|---|
| Domain запрашивает внешнюю возможность | порт в Domain | адаптер в Data | сохранить override, запросить биометрию |
| платформа сообщает о пользовательском вводе | контракт App | адаптер в App/Presentation | `KeyboardEvent` → нормализованный ввод |
| View напрямую управляет визуальным API | локальный UI-адаптер | рядом с компонентом | focus, animation, measurement |

Не каждый внешний API требует Domain-порта. Если событие имеет смысл только как жест интерфейса, достаточно границы App. Порт в Domain нужен, когда от возможности зависит бизнес-сценарий и её необходимо заменить в тестах.

## Перевод, а не простая обёртка

Хороший адаптер:

- принимает типы конкретной платформы только на внешней стороне;
- нормализует значения и формирует тип приложения;
- преобразует ошибки SDK в устойчивые failure-типы;
- скрывает проверку поддержки, разрешений и версий API;
- не возвращает наружу `KeyboardEvent`, response SDK или platform-specific enum;
- имеет контракт жизненного цикла, если создаёт подписку.

Обёртка, которая повторяет сигнатуру библиотеки один в один, зависимости не изолирует: при замене SDK изменятся все её потребители.

## Ввод с клавиатуры

У клавиатурного события есть как минимум два разных представления:

- `key` описывает получившийся символ и зависит от раскладки;
- `code` описывает физическое положение клавиши и обычно стабильно между раскладками.

Выбор является продуктовым правилом. Для сочетаний, которые должны работать на одной физической клавише в русской и английской раскладках, адаптер передаёт `code`. Для текстового редактора и мнемонических команд может требоваться `key`. Смешивать оба режима в одной строке сочетания без явного признака нельзя.

Адаптер ввода также нормализует модификаторы, игнорирует чистое нажатие модификатора, определяет политику `repeat` и передаёт признак редактируемого элемента. Решение «можно ли выполнить действие в текущем scope» остаётся в менеджере команд, а не в DOM-listener.

## Различия платформ

Названия клавиш, основной модификатор (`Control`/`Meta`), доступность API и поведение разрешений отличаются. Внутренний контракт должен выражать смысл, например `primaryModifier`, `permissionDenied` или `unsupported`, а platform adapter уже выбирает конкретное значение.

Проверка поддержки выполняется до вызова возможности. Отсутствующий API — ожидаемый результат capability check, а не авария приложения.

При SSR нельзя обращаться к `window`, `document` и нативным модулям во время импорта. Адаптер создаётся в composition root для подходящей среды либо лениво подключается после появления платформы.

## Подписки и очистка

Если адаптер регистрирует listener, observer или callback SDK, операция подключения возвращает функцию очистки или объект `Disposable`. Владельцем подписки является тот App-компонент или runtime-сервис, который её создал.

Повторный mount не должен удваивать обработчики. Cleanup обязан снимать именно ту функцию, которая была зарегистрирована, останавливать таймеры и отменять поддерживаемые незавершённые операции.

## Разрешения и приватность

Адаптер различает как минимум:

- возможность не поддерживается;
- разрешение ещё не запрашивалось;
- пользователь отказал временно;
- доступ запрещён системными настройками;
- операция была отменена;
- SDK завершился технической ошибкой.

App решает, когда показывать объяснение и предлагать переход в настройки. Domain не знает формулировок системных диалогов. В логи не попадают сырые данные камеры, биометрии, координаты и содержимое защищённого хранилища.

## Тестирование

Для адаптера полезны contract tests и таблица платформенных входов:

- одинаковый физический ввод при разных раскладках;
- `Control` и `Meta` для поддерживаемых ОС;
- удержание клавиши и `repeat`;
- ввод внутри `input`, `textarea` и contenteditable;
- отсутствующий API;
- каждый статус разрешения;
- повторное подключение и cleanup;
- преобразование неизвестной ошибки SDK в безопасный failure.

Domain и use cases тестируются с fake-портом, без эмуляции браузера или нативного SDK. Сам адаптер проверяется отдельно на границе платформы.

## Чек-лист

- [ ] Определено направление взаимодействия: Domain → платформа или платформа → App.
- [ ] Типы SDK не пересекают границу адаптера.
- [ ] Выбор logical/physical input зафиксирован как продуктовое правило.
- [ ] Поддержка API и разрешения выражены явными состояниями.
- [ ] SSR/import не обращается к недоступным глобальным объектам.
- [ ] У каждой подписки есть определённый владелец и cleanup.
- [ ] Ошибки переведены в типы приложения и не показываются пользователю напрямую.
- [ ] Адаптер покрыт таблицей платформенных случаев.
