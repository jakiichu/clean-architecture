# Введение в чистую архитектуру

Эта документация — практический справочник по проектированию клиентских приложений на **React и TypeScript** с использованием идей Clean Architecture и MVVM. Её задача — не предложить универсальное дерево папок, а объяснить, **где проходят границы ответственности, почему они находятся именно там и как принимать решения в неоднозначных ситуациях**.

В качестве сквозного контекста рассматривается приложение с достаточно сложным поведением: несколькими внешними источниками, локальным хранением, кэшированием, offline-first сценариями и полноценными пользовательскими операциями. Такой пример нужен, чтобы роли Domain, Data и App проявлялись естественно, а use case не сводились к переименованным HTTP-запросам.

## Какую проблему решает архитектура

Клиентское приложение быстро перестаёт быть набором экранов. Оно начинает:

- получать данные из нескольких API и системных возможностей устройства;
- хранить часть состояния локально;
- работать при нестабильной сети;
- синхронизировать изменения;
- проверять бизнес-ограничения;
- поддерживать несколько представлений одних данных;
- обрабатывать ошибки на разных уровнях.

Без явных границ эти обязанности смешиваются в компонентах, хуках и сервисах. UI начинает решать, откуда брать данные, репозиторий — определять бизнес-поведение, а формат ответа API распространяется по всему приложению. В результате локальное изменение затрагивает несвязанные части системы.

Clean Architecture уменьшает эту связанность, разделяя причины для изменения:

- изменение бизнес-правила затрагивает Domain;
- замена API, базы или стратегии кэша затрагивает Data;
- изменение экрана, навигации или способа отображения затрагивает App.

Архитектура не устраняет сложность предметной области. Она делает сложность **локализованной, видимой и проверяемой**.

## Модель, используемая в документации

В основе лежат три слоя:

```text
App ───────→ Domain ←────── Data
 UI           правила       источники
 MVVM         сценарии      хранение
 навигация    контракты     адаптеры
```

Стрелка показывает направление зависимости исходного кода, а не порядок выполнения программы.

Во время выполнения Domain может вызвать репозиторий, реализация которого находится в Data. Однако интерфейс этого репозитория объявлен со стороны Domain, поэтому именно Data зависит от Domain, а не наоборот. Это и есть инверсия зависимости.

### App

Слой `App` отвечает за взаимодействие с пользователем:

- React-компоненты и экраны;
- ViewModel;
- UI State и UI Effects;
- UI-модели и форматирование;
- навигацию и жизненный цикл интерфейса.

App запускает use case и отображает их результат. Он не должен знать, через какой API пришли данные, где расположен кэш и как устроена таблица локальной базы.

### Domain

Слой `Domain` описывает смысл приложения:

- сущности и объекты-значения;
- инварианты и бизнес-правила;
- пользовательские и системные сценарии;
- domain-сервисы;
- контракты репозиториев и других внешних возможностей;
- доменные ошибки.

Domain не импортирует React, Axios, TanStack Query, IndexedDB или браузерные API. Он формулирует, **что требуется приложению**, но не знает, **какой технологией это будет выполнено**.

### Data

Слой `Data` знает, как взаимодействовать с внешним миром:

- REST, GraphQL и сторонние SDK;
- локальные базы и браузерные хранилища;
- файловую систему и системные API;
- DTO и модели хранения;
- мапперы, сериализаторы и парсеры;
- кэширование, технические повторы и синхронизацию;
- реализации репозиториев и других портов Domain.

Data может выбирать между удалённым источником, локальной записью и кэшем. Но он не должен решать, какое действие допустимо пользователю или каким должен быть бизнес-результат сценария.

## Как проходит один сценарий

Рассмотрим действие «добавить место в день поездки»:

```text
Пользователь
    ↓
View передаёт действие
    ↓
ViewModel запускает AddPlaceToTripDay
    ↓
Use case загружает Trip через контракт TripRepository
    ↓
Domain проверяет дату и ограничения плана
    ↓
Реализация репозитория сохраняет результат
    ↓
ViewModel формирует новое UI State
    ↓
View отображает результат
```

У каждого участника здесь одна роль:

- View не знает бизнес-правил;
- ViewModel не выполняет HTTP-запрос;
- use case не управляет спиннером и навигацией;
- Repository не решает, разрешено ли добавление места;
- Data Source не возвращает готовую модель экрана.

Именно такое разделение, а не количество классов или директорий, является главным признаком чистой архитектуры.

## Что считается настоящим use case

Use case выражает законченное намерение пользователя или системы:

- создать поездку;
- подготовить обзор поездки;
- добавить место в конкретный день;
- сгенерировать план с учётом погоды и маршрутов;
- синхронизировать локальные изменения.

Метод вида `getWeather()`, который только перенаправляет вызов репозиторию, не становится полезным use case автоматически. Отдельный сценарий оправдан, когда он:

- выражает понятное действие на языке предметной области;
- координирует несколько шагов или зависимостей;
- применяет правила и формирует осмысленный результат;
- создаёт устойчивую границу между UI и бизнес-поведением.

Простой сценарий также допустим, если эта граница нужна приложению. Важна не длина реализации, а её архитектурный смысл.

## Repository и Data Source — не одно и то же

`Repository` представляет необходимую Domain возможность и говорит на языке предметной области:

```text
TripRepository
WeatherRepository
PlaceRepository
```

`Data Source` представляет один конкретный технический источник:

```text
WeatherRemoteDataSource → Weather API
TripLocalDataSource     → IndexedDB
LocationDataSource      → Geolocation API
```

Реализация репозитория может координировать несколько Data Source, выбирать кэш, обрабатывать отсутствие сети и преобразовывать внешние модели в доменные. Поэтому Data — это не просто папка с реализациями репозиториев, а полноценная инфраструктурная граница приложения.

## Что означает MVVM в React

В этой документации MVVM используется как правило разделения presentation-слоя, а не как требование писать ViewModel в виде класса:

```text
View (React component)
    ↓ actions
ViewModel (custom hook или объект)
    ↓
Use Cases
    ↓
Domain contracts
```

- **View** отображает состояние и отправляет пользовательские действия;
- **ViewModel** вызывает сценарии, управляет загрузкой и ошибками, создаёт UI-модель;
- **Model** представлена результатами и правилами Domain, а также доступными через него данными.

React-хук может выполнять роль ViewModel. Но хук не должен одновременно становиться HTTP-клиентом, репозиторием, контейнером зависимостей и местом бизнес-валидации.

## Архитектура — не количество абстракций

Чистая архитектура не требует создавать интерфейс, фабрику и маппер для каждой функции. Абстракция оправдана, если она:

- защищает границу между слоями;
- скрывает изменяемую техническую деталь;
- имеет самостоятельную ответственность;
- упрощает проверку поведения;
- позволяет независимо развивать части системы.

Например, отдельный Data Source полезен, когда источник можно заменить, он используется несколькими репозиториями или требует собственного тестирования. Оборачивать единственную стабильную строку кода в несколько слоёв только ради симметрии не нужно.

Сначала определяется ответственность и направление изменений. Структура директорий и количество типов следуют из этого решения, а не заменяют его.

## Основные правила

1. Domain не зависит от UI и инфраструктуры.
2. App не обращается напрямую к API и хранилищам.
3. Data реализует внешние возможности, необходимые Domain.
4. Бизнес-правила находятся в сущностях, domain-сервисах и use case.
5. Репозиторий координирует получение данных, но не реализует пользовательский сценарий.
6. Внешние DTO и модели хранения не покидают Data.
7. UI Model не попадает в Domain.
8. Низкоуровневые ошибки библиотек преобразуются на архитектурных границах.
9. Зависимости связываются в Composition Root, а не создаются внутри бизнес-логики.
10. Любая абстракция должна защищать реальную границу или ответственность.

## Как принимать решения дальше

Если непонятно, куда относится код, полезно спросить:

> Из-за какого изменения должен поменяться этот код?

- из-за нового бизнес-правила — вероятнее всего, Domain;
- из-за замены API, хранилища или формата данных — Data;
- из-за изменения отображения, навигации или взаимодействия — App.

Если причина — замена браузерного или нативного API, сначала определяется направление взаимодействия: внешний ресурс, запрашиваемый Domain, реализуется адаптером Data; событие пользовательского ввода переводится в типы приложения на границе App.

Это эвристика, а не автоматическое доказательство. Спорные и значимые решения следует фиксировать в ADR вместе с контекстом и последствиями.

Архитектура в этом проекте рассматривается как **живой набор правил и решений**. Она должна помогать понимать систему и безопасно её изменять. Если правило перестало служить этой цели, его следует пересмотреть и явно задокументировать причину.
