# Глоссарий

Данный раздел содержит определения ключевых терминов, используемых в документации по архитектуре. Термины сгруппированы по областям для удобства навигации. Глоссарий является живым документом и обновляется по мере развития проекта.

---

## Базовые архитектурные термины

| Термин | Определение |
|--------|-------------|
| **Clean Architecture (Чистая архитектура)** | Подход к организации системы, при котором бизнес-правила отделены от UI, баз данных, сети и фреймворков. Главная цель — сделать ядро системы независимым от заменяемых технических деталей. |
| **Слой (Layer)** | Архитектурная область с чёткой ответственностью и правилами зависимостей. В этой документации используются три основных слоя: `App`, `Domain` и `Data`. |
| **App (Presentation)** | Внешний слой приложения. Содержит React-компоненты, ViewModel, UI State, навигацию и преобразование результатов сценариев в форму, удобную для отображения. Вызывает Domain, но не реализует бизнес-правила и получение данных. |
| **Domain (Ядро)** | Центральный слой системы. Содержит модель предметной области, бизнес-правила, use case, domain-сервисы и контракты необходимых внешних возможностей. Не импортирует React, HTTP-клиенты, хранилища и другие инфраструктурные детали. |
| **Data (Инфраструктура)** | Слой получения, хранения, преобразования и синхронизации данных. Реализует контракты Domain и скрывает API, браузерные возможности, базы данных, форматы сериализации и правила технического кэширования. |
| **Dependency Rule (Правило зависимостей)** | Зависимости исходного кода направлены к ядру: `App → Domain ← Data`. Domain не зависит ни от App, ни от Data. App может обращаться к Data только в точке сборки зависимостей. |
| **Boundary (Граница слоя)** | Явная точка перехода между слоями. На границе внешний формат преобразуется во внутреннюю модель, а инфраструктурная деталь не должна просачиваться к потребителю. |
| **Contract (Контракт)** | Стабильное описание доступной операции или зависимости: интерфейс, тип входа и тип результата. Контракт говорит, что может сделать компонент, но скрывает способ реализации. |
| **Port (Порт)** | Контракт на границе ядра. Входной порт описывает способ запуска сценария, выходной — необходимую Domain внешнюю возможность, например хранилище, часы или источник местоположения. |
| **Adapter (Адаптер)** | Реализация, связывающая порт с конкретной технологией: REST API, IndexedDB, файловой системой, геолокацией или UI. Адаптер переводит данные и ошибки между форматами двух сторон. |
| **Composition Root (Точка сборки)** | Единственное место, где создаются конкретные реализации и связываются с их интерфейсами. Здесь допустимо одновременно знать о Domain и Data; бизнес-логики здесь нет. |
| **Dependency Injection (DI)** | Передача зависимостей объекту извне, обычно через конструктор или фабрику. Благодаря DI use case можно тестировать с подменными реализациями репозиториев и провайдеров. |
| **Facade (Фасад)** | Упрощённый публичный интерфейс подсистемы. В TypeScript-проекте часто выражается через `index.ts`, который экспортирует только разрешённый API модуля. |
| **ADR (Architecture Decision Record)** | Короткий документ с контекстом архитектурного решения, рассмотренными вариантами, выбранным подходом и его последствиями. |

## Domain и бизнес-модель

| Термин | Определение |
|--------|-------------|
| **Entity (Сущность)** | Объект предметной области с устойчивой идентичностью и жизненным циклом. Может содержать поведение и защищать свои инварианты, например `Trip` или `User`. |
| **Value Object (Объект-значение)** | Доменный объект без собственной идентичности, определяемый набором значений. Обычно неизменяем и валидируется при создании: `DateRange`, `Coordinates`, `Money`. |
| **Invariant (Инвариант)** | Бизнес-условие, которое должно оставаться истинным для корректного состояния модели. Например, дата окончания поездки не может быть раньше даты начала. |
| **Aggregate (Агрегат)** | Группа связанных сущностей и объектов-значений, изменяемая как единое целое. Корневая сущность агрегата контролирует его инварианты и является внешней точкой доступа. |
| **Use Case (Сценарий приложения)** | Завершённое пользовательское или системное действие: создать поездку, добавить место в план, подготовить обзор. Use case координирует доменную модель и внешние порты, но не знает о UI, HTTP и конкретном хранилище. |
| **Command (Команда)** | Тип входных данных для сценария, выражающий намерение выполнить действие. Например, `CreateTripCommand` содержит необходимые для создания поездки значения, но не детали формы или HTTP-запроса. |
| **Result (Результат сценария)** | Данные, возвращаемые use case его вызывающей стороне. Это доменный или прикладной тип, а не DTO конкретного API и не готовая модель React-компонента. |
| **Domain Service (Доменный сервис)** | Чистая бизнес-операция, которая не принадлежит естественным образом одной сущности или объекту-значению. Не выполняет I/O и не управляет UI; пример — алгоритм распределения мест по дням поездки. |
| **Domain Error (Доменная ошибка)** | Явное представление нарушения бизнес-правила: поездка не найдена, период некорректен, дневной маршрут слишком длинный. Не содержит деталей Axios, базы данных или UI-текста. |
| **Repository Contract (Контракт репозитория)** | Интерфейс, объявленный со стороны Domain и описанный языком предметной области: `TripRepository`, `WeatherRepository`. Domain вызывает его, а Data предоставляет реализацию. |
| **Provider / Gateway** | Внешний порт, который не обязан называться репозиторием. Подходит для часов, текущей геолокации, генератора идентификаторов, статуса сети и других возможностей внешнего мира. |

## Data и источники данных

| Термин | Определение |
|--------|-------------|
| **Repository Implementation (Реализация репозитория)** | Компонент Data, реализующий доменный контракт. Координирует источники, кэш и технические политики, преобразует модели и скрывает способ получения данных. Не реализует пользовательский бизнес-сценарий. |
| **Data Source (Источник данных)** | Компонент, работающий с одним конкретным источником или внешним механизмом. Например, REST API, IndexedDB, localStorage, File System Access API или Notification API. |
| **Remote Data Source** | Источник, получающий данные через сеть или внешний SDK. Знает формат запроса и ответа конкретного сервиса, но не принимает бизнес-решения. |
| **Local Data Source** | Источник локально сохранённых данных: база, key-value хранилище, файл или браузерное хранилище. Скрывает API выбранной технологии хранения. |
| **DTO (Data Transfer Object)** | Модель внешнего обмена данными, отражающая контракт API, SDK или сериализованного формата. Такой DTO принадлежит Data и не должен покидать его границы. Его важно отличать от доменного результата use case. |
| **Persistence Model (Модель хранения)** | Структура записи локальной базы или файла. Оптимизирована под хранение и миграции, поэтому может отличаться и от внешнего DTO, и от доменной модели. |
| **Mapper (Маппер)** | Компонент преобразования моделей на границе: `DTO → Domain`, `Persistence Model → Domain` или обратно. Не содержит бизнес-правил и не выполняет I/O. |
| **Serializer / Parser** | Компонент преобразования данных в формат хранения или передачи и обратно: JSON, архив, резервная копия, CBZ. Отвечает за синтаксис формата, а не за бизнес-смысл данных. |
| **Cache (Кэш)** | Временное хранилище, ускоряющее доступ или позволяющее пережить недоступность источника. Наличие записи в кэше не означает автоматически, что она достаточно актуальна. |
| **Cache Policy (Политика кэша)** | Техническое правило выбора между кэшированными и свежими данными: использовать кэш, обновить его, вернуть устаревшие данные как fallback или сообщить об отсутствии данных. |
| **Refresh Policy (Политика обновления)** | Явная стратегия актуализации данных, например `CacheFirst`, `NetworkFirst`, `IfExpired` или `ForceRefresh`. Может передаваться в репозиторий как часть требований сценария. |
| **Retry Policy (Политика повторов)** | Техническое правило повторения неуспешной I/O-операции: число попыток, задержка и перечень повторяемых ошибок. Не должна менять смысл бизнес-операции. |
| **Offline-first** | Подход, при котором локальные данные являются полноценной частью работы приложения, а сеть используется для обновления и синхронизации. Требует явных правил актуальности, конфликтов и ошибок. |
| **Synchronization (Синхронизация)** | Согласование локального и удалённого состояния: отправка накопленных изменений, получение обновлений и разрешение конфликтов. |
| **Infrastructure Error (Инфраструктурная ошибка)** | Сбой технического механизма: сеть недоступна, запрос завершился по таймауту, ответ не разобран, запись в хранилище не удалась. Data переводит библиотечные ошибки в стабильные ошибки приложения. |

## App и MVVM

| Термин | Определение |
|--------|-------------|
| **MVVM (Model–View–ViewModel)** | Способ организации presentation-слоя: View отображает состояние и отправляет действия, ViewModel запускает сценарии и формирует состояние, а Model представлена данными и правилами нижележащих слоёв. |
| **View** | React-компонент или экран, который отображает переданное состояние и сообщает о действиях пользователя. Не обращается напрямую к API и не содержит бизнес-правил. |
| **ViewModel** | Адаптер между View и use case. Запускает сценарии, управляет состояниями загрузки и ошибки, преобразует результат в UI Model и предоставляет View действия. В React может быть реализован кастомным хуком. |
| **UI Model** | Модель, подготовленная специально для отображения: локализованные подписи, форматированные даты, объединённые поля и признаки видимости. Не должна использоваться внутри Domain. |
| **UI State** | Полное состояние экрана в конкретный момент: загрузка, успешные данные, пустое состояние или ошибка, а также значения и ошибки формы. |
| **UI Effect** | Одноразовое событие presentation-слоя, которое неудобно хранить как устойчивое состояние: навигация, toast, фокус поля, открытие системного диалога. |
| **Presenter (Презентер)** | Компонент, преобразующий результат сценария в представление для UI. В MVVM его функция часто входит во ViewModel или выделенный UI Mapper. |
| **Orchestration (Оркестрация)** | Координация нескольких действий. Бизнес-последовательность относится к use case, а навигация, показ сообщений и управление UI-эффектами — к App. |
| **Guard (Страж)** | Presentation-компонент, проверяющий условие доступа к маршруту или экрану и выбирающий навигационное поведение. Само бизнес-правило доступа при необходимости делегируется Domain. |
| **Hook Adapter (Хук-адаптер)** | React-хук, который адаптирует сценарии и зависимости к жизненному циклу компонента. Он может выступать ViewModel, но не должен превращаться в место создания всего графа зависимостей. |

## Термины управления состоянием

| Термин | Определение |
|--------|-------------|
| **Server State** | Данные, источником которых является внешний API. Требуют кэширования, инвалидации и синхронизации. Управляются клиентами запросов (TanStack Query). |
| **Business State** | Инварианты и вычисляемые результаты предметной области. Не хранятся, а вычисляются в Domain при каждом вызове use-case. |
| **Persistent State** | Данные, сохраняемые между перезапусками приложения: токены, настройки, криптографические ключи. Хранятся через адаптеры в Data. |
| **Stale Time** | Время, в течение которого кэшированные данные считаются актуальными и не требуют повторного запроса. |
| **GC Time (gcTime)** | Время, в течение которого неактивные кэшированные данные хранятся в памяти после того, как подписчики отключились. По истечении — данные удаляются из кэша. |
| **Invalidation (Инвалидация)** | Процесс пометки кэшированных данных как устаревших, что инициирует их повторную загрузку при следующем обращении. |
| **Refetch (Рефетч)** | Повторный запрос данных к источнику, инициированный программно или по таймеру. |
| **Optimistic Update** | Обновление UI до получения ответа сервера, с откатом при ошибке. Допустимо только для некритичных действий. |
| **Pessimistic Update** | Обновление UI только после успешного ответа сервера. Обязательно для финансовых операций, авторизации и критичных действий. |
| **Query Key** | Уникальный идентификатор запроса в TanStack Query. Используется для адресации кэша при инвалидации. Объявляется в константе `QUERY_KEYS`. |
| **Mutation (Мутация)** | Операция изменения данных (POST/PUT/DELETE), управляемая через `useMutation`. Не кэшируется, выполняется по требованию. |
| **refetchInterval** | Параметр `useQuery`, задающий интервал автоматического рефетча в миллисекундах. Используется для polling и таймеров ротации. |
| **networkMode** | Настройка TanStack Query, определяющая поведение запросов при отсутствии сети: `'online'`, `'always'`, `'offlineFirst'`. |

## Мобильная и нативная специфика

| Термин | Определение |
|--------|-------------|
| **Native Module** | Код, написанный на платформенном языке (Swift/Kotlin) и доступный в React Native через мост (Bridge). |
| **SecureStore / Keychain / Keystore** | Аппаратно-защищённые хранилища ОС для криптографических ключей, токенов и чувствительных данных. На iOS — Keychain, на Android — Keystore. |
| **Biometric Authentication** | Аутентификация с использованием биометрических данных устройства: Face ID, Touch ID, отпечаток пальца. |
| **Device Fingerprint** | Уникальный идентификатор устройства, формируемый на основе аппаратных и программных характеристик. Используется для привязки сессии к конкретному устройству. |
| **Expo Router** | Файловая система маршрутизации для React Native на основе Expo. Обеспечивает навигацию через декларативные пути, соответствующие структуре директории `app/`. |
| **Metro Bundler** | Сборщик модулей для React Native. Трансформирует исходный код, разрешает зависимости и формирует бандл для запуска на устройстве. |
| **Development Build** | Кастомная сборка приложения для разработки, включающая нативные модули и отладочные инструменты. Отличается от Expo Go поддержкой любых библиотек. |
| **EAS Build** | Облачный сервис сборки Expo Application Services. Позволяет компилировать приложения для iOS/Android без локальной настройки Xcode/Android Studio. |
| **Deep Link** | Ссылка, открывающая конкретный экран приложения из внешнего источника (браузер, email, пуш-уведомление). Конфигурируется через `scheme` в `app.config.ts`. |
| **Safe Area** | Зона экрана, не перекрытая системными элементами (нотч, статус-бар, нижняя панель навигации). Учитывается через `SafeAreaProvider` и `useSafeAreaInsets`. |
| **Gesture Handler** | Библиотека `react-native-gesture-handler`, заменяющая встроенную систему жестов. Необходима для корректной работы навигации и свайпов. |
| **Swipe Back** | Жест смахивания экрана вправо для возврата назад (iOS-паттерн). Реализуется через кастомный `SwipeBackWrapper` или настройки стека навигатора. |
| **Background Task** | Задача, выполняемая в фоновом режиме (когда приложение свёрнуто). На мобильных платформах ограничена системой; `refetchIntervalInBackground: false` отключает polling в фоне. |
| **App State** | Состояние жизненного цикла приложения: `active`, `background`, `inactive`. Используется для управления polling и освобождения ресурсов. |
| **WHEN_UNLOCKED_THIS_DEVICE_ONLY** | Политика доступа к SecureStore: данные доступны только когда устройство разблокировано и только на текущем устройстве (не синхронизируются в облако). |

## Инструменты и библиотеки

| Термин | Определение |
|--------|-------------|
| **TanStack Query** | Библиотека для управления серверным состоянием: кэширование, фоновое обновление, пагинация, обработка ошибок. Используется в слое App. |
| **Zustand** | Минималистичная библиотека управления клиентским состоянием. Применяется для глобальных флагов интерфейса и сессионных настроек. |
| **TypeScript Strict Mode** | Набор строгих правил типизации: запрет `any`, обязательная проверка `null/undefined`, строгая проверка `this`. Обеспечивает безопасность рефакторинга. |
| **Expo Config Plugins** | Механизм настройки нативных проектов (iOS/Android) через декларативный конфиг `app.config.ts` без ручного редактирования Xcode/Gradle. |
| **axios-mock-adapter** | Библиотека для мокирования HTTP-запросов axios в тестах. Позволяет проверять маппинг ответов без реального сервера. |
| **React Testing Library** | Утилита для тестирования React-компонентов, фокусирующаяся на поведении с точки зрения пользователя. Предоставляет `renderHook` для тестирования хуков. |
| **Detox** | Фреймворк для E2E-тестирования мобильных приложений на реальных устройствах или симуляторах. |
| **MMKV** | Высокопроизводительное key-value хранилище для React Native (альтернатива AsyncStorage). Используется для незащищённых настроек и конфигурации. |

## Принципы и паттерны

| Термин | Определение |
|--------|-------------|
| **Inversion of Control (IoC)** | Принцип, при котором управление потоком программы передаётся внешнему компоненту (например, внедрение зависимостей через конструктор). |
| **Dependency Injection (DI)** | Паттерн передачи зависимостей извне, а не их создания внутри класса. Упрощает тестирование и замену реализаций. |
| **Pure Function (Чистая функция)** | Функция, которая при одинаковых входных данных всегда возвращает одинаковый результат и не имеет побочных эффектов. Основа бизнес-логики в Domain. |
| **Side Effect (Побочный эффект)** | Любое взаимодействие с внешним миром: сеть, диск, UI, навигация. Изолируется на краях системы (App или Data). |
| **Fire-and-Forget** | Сценарий выполнения операции без ожидания результата или обработки ошибки. Допустим только для аналитики и некритичных логов. |
| **Composition over Inheritance** | Принцип предпочтения композиции объектов наследованию. В проекте реализуется через фабричные функции с передачей зависимостей. |
| **Single Responsibility** | Принцип: каждый модуль, класс или функция должны иметь одну причину для изменения. Основа разделения use-case и репозиториев. |
| **Graceful Degradation** | Управляемая деградация функциональности при сбоях: приложение продолжает работу с ограниченными возможностями, а не падает. Реализуется через кэш, fallback-экраны и блокировку мутаций. |
| **Demo Mode (Режим демонстрации)** | Конфигурация, при которой сетевые зависимости заменяются mock-реализациями. Позволяет разрабатывать и демонстрировать приложение без реального бэкенда. Управляется флагом `IS_DEMO_MODE`. |
| **Polling** | Паттерн периодического запроса данных через фиксированный интервал. Реализуется через `refetchInterval` в TanStack Query. |
| **Countdown Timer** | UI-паттерн отображения обратного отсчёта до следующего события (обновление кода, истечение сессии). Управляется через `setInterval` в `useEffect`, не через Domain. |
| **Error Boundary** | React-компонент, перехватывающий ошибки рендеринга в дочернем дереве и отображающий fallback-UI вместо падения приложения. |

## Паттерны обработки ошибок

| Термин | Определение |
|--------|-------------|
| **Presentation Error** | Ошибка отображения или валидации формы. Управляется в App-слое, не доходит до Domain. |
| **isRetryable** | Флаг в интерфейсе ошибки, указывающий, имеет ли смысл повторить операцию. Таймауты и 5xx — retryable, 4xx и доменные ошибки — нет. |
| **Fallback UI** | Запасной интерфейс, отображаемый при ошибке или отсутствии данных. Предотвращает показ пустого экрана пользователю. |

## Конфигурация действий и пользовательские настройки

| Термин | Определение |
|--------|-------------|
| **Action ID (Идентификатор действия)** | Стабильный технический идентификатор пользовательской или системной команды, не зависящий от локализованной подписи, React-компонента и конкретного способа запуска. Например, `global-search.open`. Используется для связи definition, пользовательской настройки и обработчика действия. |
| **Action Catalog (Каталог действий)** | Полный набор известных системе действий и их неизменяемых характеристик. Каталог является источником истины для стандартной конфигурации и не должен собираться динамически из смонтированных UI-компонентов. |
| **Definition (Определение)** | Неизменяемое системное описание элемента конфигурации: идентификатор, стандартное значение, область, политики и доступность изменения. Definition отвечает на вопрос «что предусмотрено приложением по умолчанию». |
| **Override (Пользовательское переопределение)** | Сохранённое отклонение от definition. Содержит только пользовательское решение: назначенное значение или явное отключение. Отсутствие override означает использование definition. |
| **Effective Configuration (Эффективная конфигурация)** | Конфигурация, фактически действующая после применения override к definition. Вычисляется, а не хранится как отдельный источник истины. |
| **Explicit Disabled State (Явное отключение)** | Отдельный вариант модели, означающий намеренное отключение элемента. Не эквивалентен отсутствию override: отсутствие изменения возвращает стандартное поведение. |
| **Reset to Default (Сброс к стандартному)** | Удаление пользовательского override, после которого effective configuration снова вычисляется из актуального definition. Не требует копировать стандартное значение в persistent storage. |
| **Canonicalization (Канонизация)** | Преобразование нескольких эквивалентных представлений в одну стабильную форму для сравнения, индексирования или поиска конфликтов. Например, `Shift+Control+K` и `Control+Shift+k` преобразуются в одинаковый ключ. Каноническая форма не обязана быть отображаемой пользователю строкой. |
| **Scope (Область действия)** | Контекст, в котором команда или правило активно: глобальный, экранный, модальный или относящийся к конкретному инструменту. Scope используется для определения пересечения команд и допустимости одинаковой конфигурации. |
| **Conflict Policy (Политика конфликтов)** | Явное правило, определяющее, могут ли два элемента иметь одинаковое назначение. Политика учитывает effective state, scope и идентичность элемента и принадлежит Domain, если выражает устойчивое правило продукта. |
| **Repeat Policy (Политика повтора)** | Правило обработки удерживаемого ввода: разрешить повторные события или выполнить действие только один раз до отпускания клавиши. Семантика политики принадлежит модели команды, а техническая реализация — App adapter. |
| **Logical Key (Логическая клавиша)** | Значение ввода после применения раскладки и состояния модификаторов, обычно представленное `KeyboardEvent.key`: `и`, `B`, `ArrowLeft`. Подходит, когда важен получившийся символ или служебное назначение клавиши. |
| **Physical Key (Физическая клавиша)** | Положение клавиши на клавиатуре, обычно представленное `KeyboardEvent.code`: `KeyB`, `Slash`, `Digit7`. Используется, когда назначение должно сохраняться при смене раскладки. |
| **Input Adapter (Адаптер ввода)** | Компонент App, преобразующий события конкретной платформы или библиотеки в модель приложения и обратно. Он согласованно применяет политику физических и логических клавиш при записи и исполнении команды. |
| **Runtime Validation (Runtime-валидация)** | Проверка неизвестных данных во время выполнения на внешней границе. Необходима для результатов `JSON.parse`, API-ответов и persistent storage, поскольку TypeScript не подтверждает их фактическую структуру. |

Подробнее: [пример менеджера горячих клавиш](./examples/hotkey-manager.md).

**Platform Adapter (платформенный адаптер)** — реализация границы между приложением и браузером, ОС или нативным SDK. Переводит внешние события, значения и ошибки в устойчивые типы приложения и управляет техническим жизненным циклом интеграции.

**Capability Check** — явная проверка доступности платформенной возможности до её использования. Результат `unsupported` является ожидаемым состоянием, а не исключением.

**Disposable / Cleanup** — контракт освобождения ресурса: снятия listener, остановки observer или отмены поддерживаемой операции. Владельцем cleanup является компонент или runtime-сервис, создавший подписку.

Подробнее: [платформенные адаптеры](./cross-cutting/platform-adapters.md).
